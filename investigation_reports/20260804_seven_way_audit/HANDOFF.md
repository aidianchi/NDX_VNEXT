## 二、必读的四条教训（不读会重复踩）

### 教训 1：单路审计只能产出"证据"，不能产出"结论"

**七路里有三路把严重度报高了，全部被主对话改判。** 原因不是能力不足，是上下文隔离的必然代价：

| 报告 | 主对话改判 | 它看不到什么 |
|---|---|---|
| 数据层报 P0「回测时点泄漏」 | **P1** | 下游 `data_evidence.py:645` 硬拦 + `packet_builder.py:473` 把它排除出 packet，脏数据走不到模型面前 |
| 证据链报 P0「权限防线覆盖率个位数」 | **P1** | 受保护的那 8 条恰好是**全部可发布结论 + 行动翻译**；它拿"字符量"当分母 |
| 测试报 P0「两个文件误入 git」「pandas 越界」 | **P2 / P1** | 文件内容无敏感信息；pandas 越界当下无故障 |

**判据：严重度必须在全链路上评定，不能在单个模块内评定。** 分路的产出是证据，结论只能在汇总层产生。

**同时反过来**：如果只派一路"整体审计"，它两头都看得到但两头都看不深——数据层那个泄漏是靠一条真实复现命令挖出来的，泛泛扫一遍挖不出来。**并行拆分 + 汇总层复核，两者缺一不可。**

### 教训 2：分母选错，真问题会被说成假问题

证据链那路的"覆盖率个位数"是错的，但它指的缺口是真的。正确表述是：

> **权限校验覆盖 headline claims（8 条），不覆盖 supporting narrative（20 万字级）。**

而用户的实测阅读路径是「通读完整判断书、L1-L5 常看、审计区不看」——**未受保护面恰为用户主要阅读面**。同一事实换个分母，从"可以不管"变成"最该管"。

### 教训 3：修边界的那次改动，最容易在边界上开新口

T39 的 PIT 泄漏由 2026-07-11 commit `860971d` 引入，而**那次改动的标题正是 "PIT earnings contract"**——目标就是时点纪律。

**规律**：改动目标是加固某条边界时，改的人注意力全在"我要拦住的那条路"上，**顺手加的兜底/降级分支没过同一套审查**。以后凡是"加固边界"类改动，兜底分支必须单独复核一遍。

### 教训 4：模型说"数据缺失"时，先查它的输入里到底有没有那个数

`integrated_adjudicator` 说"本轮输入未提供 VXN 数值和分位"——**它说的是准确的实话**，同一份报告的 L2 层却完整显示 `VXN=30.84 / 87.2 分位`。扫全站后发现：**该站 26 个 `L#.get_*` 允许引用里，20 个只有名字和许可、没有数值。**

**VXN 之所以被发现，只因为它恰好是一道直接提问的主语。另外 19 条没有同等力度的追问兜着——系统这次是被模型的诚实救的，不是被机制救的。**

学界给这类失败起过名字：MAST 论文（arXiv 2503.13657）的 **FM-2.4 "Information withholding"**。**不是本项目独有的低级错误，也不会自己消失。**

## 四、主方向 T38 的思想（完整版见 WORK_ORDERS.md 第三节）

**问题的形状**：全量推送这个机制**本身强加了一个两难**——塞满则贵且稀释注意力，剪枝则丢失未来材料并把菜单固化成当下视角。T37 就卡死在这里（想砍 68 条从未被引用的，但「菜单不得先天偏科」是常驻边界）。

**用户提出的第三条路**：这很像 **Skill 的核心机制**——常驻只有名字 + 一行说明，判断用得上才加载完整内容，再往下还有更细的材料按需读。**三层递进。**

**关键洞察**：「知道有这个东西」和「知道这个东西的全部内容」是两件事，**成本差两个数量级，而前者已足够让 agent 判断需不需要它**。

**三条设计原则**：
1. **广度常驻，深度按需**——一条不砍，保住「菜单不得先天偏科」。
2. **索引即许可**——"能取到"就是"有许可"。当前"引用许可"与"数值供给"分处两个拼装点，VXN 就死在这条缝里；合并成一个动作，缝在物理上消失。这是「轨道 > 导出 > 规矩」第①档。
3. **筛选必须留痕**——选中哪 K 条、依据、被排除的编号，全部落盘。

**必须避开的陷阱**：相关性锚点必须是「**该站声明的问题**」，**绝不能是「哪一方的结论」**。外部调研发现 TradingGPT 正是给多空双方各自独立记忆库——**那会直接违反「菜单不得先天偏科」**。安全做法：**正反双方用同一次检索、同一份 top-K，只有立场措辞不同。**

## 五、T45：A/B 之争与"是否重建"的研究设计

### 事实前提（已核实，不要重新推翻）

`_run_stage`（`orchestrator.py:5230`）每次 attempt **只调用一次** `call_with_fallback`，取 `tool_calls[0].function.arguments` 当**输出**；`llm_engine.py:519-523` **无工具结果回灌**。

> **工具通道是"交答卷"的载体，不是"要材料"的能力。当前站点无法自主取用。**

主对话初稿曾写"它自己开口要"，**该说法已作废**，由外部调研纠正、主对话核实代码后更正。

### 两个变体

| | **变体 A：代码侧检索** | **变体 B：模型侧按需取用** |
|---|---|---|
| 谁决定取哪些 | 编排代码在组装提示词**之前**按该站声明的问题做相关性排序 | 模型自己发起取用调用 |
| 改动面 | 只改组装逻辑，站点仍是单次调用 | 单次调用改成循环 |
| 新增失败面 | 无 | 有（`tool_choice="auto"` 下模型可不走工具通道，已实证；循环化放大该缺口） |
| 前缀缓存 | 不冲突 | 增加往返，破坏前缀稳定 |
| **审计所得** | "代码筛了哪 K 条、依据、排除了哪些" | **"它主动要了哪几条"** |

**审计价值的差别是实质性的**：只有 B 能给出"模型想要什么"这个当前完全拿不到的信号；A 给出的是"我们按什么规则筛的"——仍强于现状，但不是同一类信息。

### 用户提出的第三条路：基于外部 harness 重建

用户原话："版本 b 我怀疑可以基于 pi 重新搭建这个架构了。"

**主对话必须记录的一条风险（不是否决，是必须单独论证的红线）**：

> 「层间隔离」是本项目**代码强制、且本次用真实提示词文本实测干净**的资产（五层 `apparent_cross_layer_signals` 全空、`bridge_memo`/`thesis_draft`/`final_adjudication` 五层零命中）。**外部 harness 的上下文模型未必提供等价强制——重建等于把一条已验证的边界交给别人的实现。**
>
> 外部调研另有佐证：Cognition 十个月内推翻自己，从"share full agent traces"改为发现干净隔离的评审 agent 表现更好。**通用 harness 的默认倾向是共享，不是隔离。**

### 研究必须回答的四问

1. 两变体各自的可审计性所得，值不值它的代价？
2. B 的循环化新增失败面有多大？（严格模式是概率性保证，已实证）
3. **重建路线：外部 harness 能否提供等价的层间隔离强制？** 不能则整条路线的代价要重新计。
4. 迁移成本 vs 留在现架构做 A 的成本。

**只出报告不动刀。不预设结论。**
