## 二、必读的五条教训（不读会重复踩）

### 教训 0：谈"隔离"之前先问"防的是哪条通道"

主对话 2026-08-05 在此栽过一次：把「层间隔离」的迁移风险写成"外部 harness 未必提供等价强制"，被用户当场质疑——**harness 的 subagent 确实能隔离上下文**（Codex `spawn_agent` 源码确认默认不继承父级历史）。

**分清两件事**：subagent 隔离防的是**未授权的继承**（父级历史自动流入）；NDX 层间隔离防的是**授权者本人的编写**（提示词内容本身）。前者是框架默认值，后者靠 `_build_layer_*` 按层索引机械构造。**subagent 给你一间干净的房间，但门是你自己开的。**

完整论证与更正见第五节。**凡涉及"某某机制能不能保证隔离"的判断，先落到"它防哪条通道"，再下结论。**


### 教训 1：单路审计只能产出"证据"，不能产出"结论"

**七路里有三路把严重度报高了，全部被主对话改判。** 原因不是能力不足，是上下文隔离的必然代价：

| 报告 | 主对话改判 | 它看不到什么 |
|---|---|---|
| 数据层报 P0「回测时点泄漏」 | **P1** | 下游 `data_evidence.py:645` 硬拦 + `packet_builder.py:562-575` 把命中指标整条置空剔除，脏数据走不到模型面前（2026-08-05 复核订正：旧版写 `:473`，那是 successful_indicators 计数器，不剔数据）|
| 证据链报 P0「权限防线覆盖率个位数」 | **P1** | 受保护的 8 条覆盖 headline 结论与行动翻译；它拿"字符量"当分母（2026-08-05 复核订正："恰好是全部可发布结论"不成立——`reasoned_verdict`（本轮 1,472 字符的主判决正文）不在 8 条内，只有 `_validate_reasoned_verdict_refs` 弱校验；另 `[:6]`/`[:4]` 硬截断会让超出条目无声掉出保护面。改判 P1 仍成立）|
| 测试报 P0「两个文件误入 git」「pandas 越界」 | **P2 / P1** | 文件内容无敏感信息；pandas 越界当下无故障 |

**判据：严重度必须在全链路上评定，不能在单个模块内评定。** 分路的产出是证据，结论只能在汇总层产生。

**同时反过来**：如果只派一路"整体审计"，它两头都看得到但两头都看不深——数据层那个泄漏是靠一条真实复现命令挖出来的，泛泛扫一遍挖不出来。**并行拆分 + 汇总层复核，两者缺一不可。**

### 教训 2：分母选错，真问题会被说成假问题

证据链那路的"覆盖率个位数"是错的，但它指的缺口是真的。正确表述是：

> **权限校验覆盖 headline claims（8 条），不覆盖 supporting narrative（20 万字级）。**

而用户的实测阅读路径是「通读完整判断书、L1-L5 常看、审计区不看」——**未受保护面恰为用户主要阅读面**。同一事实换个分母，从"可以不管"变成"最该管"。

### 教训 3：加固某条边界时，必须回头复查同区域**既有**的兜底分支

#### ⚠️ 本条已于 2026-08-05 红队复核改写——旧版归因被 git 证伪，不要沿用

**旧版写的是**：泄漏由 2026-07-11 commit `860971d`（标题正是 "PIT earnings contract"）引入，规律是"加固边界的改动顺手开新口"。

**`git log -S` 实查**（Fable 亲手复验）：`eps_revision_primary_source = "yfinance_fallback"` 与 `:3323` 的 `and not end_date` 均由 **`5705a71`（2026-06-08，"Refine L4 data sources"，一次普通的数据源改造）** 引入，早于 860971d 一个月。旧版的机制——"加固时顺手加的兜底没过审查"——在这个实例上**零支撑**。

**真实发生的事更平常**：六月有人加 fallback 没配 PIT 守卫；七月有人在同一区域做时点加固时，没有回头复查既有兜底。**改写后的规律**：凡"加固边界"类改动，验收范围必须包含同区域**既有**的兜底/降级分支，不只是本次新写的代码。同文件里 capex/buyback 的 yfinance fallback 守法正确（`tools_L4.py:5806-5827`/`:6224-6245`），T39 可照抄。

**附带教训**：审计里所有"由 commit X 引入"的单提交归因，都应做 `git log -S` 十秒检查——本条即是没做而写错的实例。

### 教训 4：模型说"数据缺失"时，先查它的输入里到底有没有那个数

`integrated_adjudicator` 说"本轮输入未提供 VXN 数值和分位"——**它说的是准确的实话**，同一份报告的 L2 层却完整显示 `VXN=30.84 / 87.2 分位`。扫全站后发现：**该站 26 个 `L#.get_*` 允许引用里，20 个只有名字和许可、没有数值。**

**VXN 之所以被发现，只因为它恰好是一道直接提问的主语。另外 19 条没有同等力度的追问兜着——系统这次是被模型的诚实救的，不是被机制救的。**

**2026-08-05 红队复核增补：实际比 20/26 更糟。** 所谓 6 条"非 hollow"逐条看：2 条只出现在提示词模板的格式示例里、1 条是被更长 ref 名子串误命中、3 条只在 `reasoned_verdict` 散文里当方括号引用——**结构化数值供给实为 0/26**。

学界给这类失败起过名字：MAST 论文（arXiv 2503.13657）的 **FM-2.4 "Information withholding"**。**不是本项目独有的低级错误，也不会自己消失。**

## 四、主方向 T38 的思想（完整版见 WORK_ORDERS.md 第三节）

**问题的形状**：全量推送这个机制**本身强加了一个两难**——塞满则贵且稀释注意力，剪枝则丢失未来材料并把菜单固化成当下视角。T37 就卡死在这里（想砍 68 条从未被引用的，但「菜单不得先天偏科」是常驻边界）。

**用户提出的第三条路**：这很像 **Skill 的核心机制**——常驻只有名字 + 一行说明，判断用得上才加载完整内容，再往下还有更细的材料按需读。**三层递进。**

**关键洞察**：「知道有这个东西」和「知道这个东西的全部内容」是两件事，**成本差两个数量级，而前者已足够让 agent 判断需不需要它**。

**三条设计原则**：
1. **广度常驻，深度按需**——一条不砍，保住「菜单不得先天偏科」。
2. **索引即许可**——"能取到"就是"有许可"。当前"引用许可"与"数值供给"分处两个拼装点，VXN 就死在这条缝里；合并成一个动作，缝在物理上消失。这是「轨道 > 导出 > 规矩」第①档。
3. **筛选必须留痕**——选中哪 K 条、依据、被排除的编号，全部落盘。

**必须避开的陷阱**：相关性锚点必须是「**该站声明的问题**」，**绝不能是「哪一方的结论」**。外部调研发现 TradingGPT 正是给多空双方各自独立记忆库——**那会直接违反「菜单不得先天偏科」**。安全做法：**正反双方用同一次检索、同一份 top-K，只有立场措辞不同。**

## 五、T45：A/B 之争与"是否重建"的研究设计

### 事实前提（已核实，不要重新推翻）

`_run_stage`（`orchestrator.py:5230`）每次 attempt **只调用一次** `call_with_fallback`，取 `tool_calls[0].function.arguments` 当**输出**；`llm_engine.py:519-523` **无工具结果回灌**。

> **工具通道是"交答卷"的载体，不是"要材料"的能力。当前站点无法自主取用。**

主对话初稿曾写"它自己开口要"，**该说法已作废**，由外部调研纠正、主对话核实代码后更正。

### 两个变体

| | **变体 A：代码侧检索** | **变体 B：模型侧按需取用** |
|---|---|---|
| 谁决定取哪些 | 编排代码在组装提示词**之前**按该站声明的问题做相关性排序 | 模型自己发起取用调用 |
| 改动面 | 只改组装逻辑，站点仍是单次调用 | 单次调用改成循环 |
| 新增失败面 | 无 | 有（`tool_choice="auto"` 下模型可不走工具通道，已实证；循环化放大该缺口） |
| 前缀缓存 | 不冲突 | 增加往返，破坏前缀稳定 |
| **审计所得** | "代码筛了哪 K 条、依据、排除了哪些" | **"它主动要了哪几条"** |

**审计价值的差别是实质性的**：B 能给出**事前**的取用意图；A 给出"我们按什么规则筛的"。（2026-08-05 复核订正：旧版"只有 B 能给出模型想要什么"**不成立**——存在中间形态 **A′**：代码侧深度分档 + 在站点输出 schema 里加必填的 `unmet_information_needs`（ref 枚举），**零往返、零新增失败面、严格模式可强制**，拿到的是**事后**的缺料回报，可直接反哺筛选器。VXN 事件里模型正是在散文里说出了这句实话——A′ 就是把那句实话从散文搬进 schema，把"被诚实救"变成"被机制救"。另两个中间形态：两遍单发（先发索引收 `needed_refs` 再重跑，两次都是单次调用）；按站点切（重复量集中在治理四站，可只动一个构造函数）。**B 不需要重建架构**——循环化是在 `_run_stage` 内加回灌，不是换 harness，勿把 B 与重建绑在一起。）

### 用户提出的第三条路：基于外部 harness 重建

用户原话："版本 b 我怀疑可以基于 pi 重新搭建这个架构了。"

#### ⚠️ 本节风险表述已于 2026-08-05 更正——旧版说法作废，不要沿用

**旧版写的是**："外部 harness 的上下文模型未必提供等价强制，重建等于把一条已验证的边界交给别人的实现。"

**用户当场质疑**："层间隔离不是 subagent 完全能做到的吗？至少 claudecode 的 subagent 就可以隔离上下文。"

**质疑成立，旧表述过宽且暗示错误。** harness 的 subagent **确实**隔离上下文——外部调研已从源码确认 Codex `spawn_agent` **默认不继承父级对话历史**，比很多人以为的更严格。说"外部 harness 隔离能力弱"是错的。

#### 关键区别：两种隔离防的不是同一条通道

| | 防的是什么 | 谁来保证 |
|---|---|---|
| **harness subagent 隔离** | 未授权的**继承**（父级历史自动流入） | 框架默认值 |
| **NDX 层间隔离** | 授权者本人的**编写**（提示词内容本身） | 代码按层索引**机械构造** |

**subagent 隔离给你一间干净的房间，但门是你自己开的，你想搬什么进去都行。**

**活体反例（本次会话自身）**：主对话手写了 9 个 subagent 的 brief，并**主动跨方向注入**——给第八路（上下文实测）的任务书里直接写入了源自主对话自身分析的 VXN 线索。**subagent 隔离未构成任何阻碍，因为它不设计用于阻止这个。**

#### NDX 的做法是构造侧机械导出，不是继承侧默认隔离（已核实代码）

`orchestrator.py:930-943` `_build_layer_stage_payload` —— 6 键固定白名单，每个键按 `layer` 索引：
```python
"layer_facts":    _model_dump(packet.facts_by_layer.get(layer)),
"layer_raw_data": packet.raw_data.get(layer, {}),
"runtime_boundary_policy_id": "layer_runtime_input_policy_v1",
```

`orchestrator.py:5089-5112` `_build_layer_context_brief` —— **不是过滤，是重建**：
```python
layer_highlights = {layer: list(context_brief.layer_highlights.get(layer, []))}
return ContextBrief(..., apparent_cross_layer_signals=[], ...)   # 硬编码为空
```

> **没有人在"克制自己不写别层的东西"——是根本没有能写进去的位置。** 这是「轨道 > 导出 > 规矩」第①档，且连"写 brief 的人"都被物理排除。

#### 更正后的三条结论（T45 据此立论）

1. **"重建会丢掉层间隔离"这个担忧基本不成立。** 构造侧那一层本来就不是地基提供的，是 `_build_layer_*` 提供的；换任何地基都得自己写一遍，**不构成迁移损失**。
2. **真实风险是反向的，而且更实在**：harness 的增值功能——跨 agent 记忆、自动压缩（compaction）、检索、共享状态——**它们存在的目的就是"把相关的上下文找回来"，而"跨层相关"在本项目恰恰被禁止**。迁移后将**持续地在关闭该 harness 的核心卖点**；每次版本升级都要重新确认这些"帮你带回有用信息"的机制没有把 L2 的结论带进 L3。（Cognition 十个月内从 "share full agent traces" 反转为"干净隔离的评审 agent 表现更好"，佐证通用框架的默认倾向是共享。）
3. **隔离必须可事后证明，不只是可能成立。** 本次能确认干净，靠的是 grep `prompt_audit/**/*.prompt.txt` 里**真正发出去的字节**（五层 `apparent_cross_layer_signals` 全空、`bridge_memo`/`thesis_draft`/`final_adjudication` 关键字五层零命中）。**任何重建必须保留等价落盘物**，否则边界即使守住也无法证明——而"可审计推理链"是北极星，证明不了等于没有。

### 研究必须回答的四问（2026-08-05 复核增补：先答第 0 问，再看四问）

**第 0 问（重建路线专用，答否即终止）**：本次审计定位的缺陷（幽灵许可 / 预算截断 / PIT 泄漏 / L3-L5 零登记 / 严格模式不留痕），有几条的根因位于 harness 层？**若为零，重建修不了任何已知缺陷，重建部分的第 3/4 问不必展开。**（复核时逐条对照：五条根因分别在拼装代码、拼装代码、数据层、合约层、自家产物——**无一在 harness 层**。）

1. 两变体各自的可审计性所得，值不值它的代价？**（须把 A′ 一并纳入比较，见上方 2026-08-05 订正）**
2. B 的循环化新增失败面有多大？（严格模式是概率性保证，`tool_choice="auto"` 下模型可不走工具通道已实证）
3. **目标 harness 有哪些会自动向上下文注入内容的机制**（跨 agent memory / auto-compaction / retrieval / shared state）？**能否全部关闭？关闭之后它还剩多少价值**（成熟重试、并发、可观测性等）是否仍支撑迁移成本？——**若答案是"关完只剩进程管理器"，重建理由不成立。**
4. 迁移成本 vs 留在现架构做 A 的成本；以及重建后如何保留等价于 `prompt_audit` 的可审计落盘物。

**只出报告不动刀。不预设结论。且必须在调研开始前把"满足什么条件才建议迁移/选 B"的决策规则写下落盘，调研结束后不得修改该规则**——否则本研究只会为已经想做的事找理由（2026-08-05 复核增补）。
