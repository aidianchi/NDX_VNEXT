## 一、A 面 5 问逐条裁决

### Q1 · 可复现：同一 `effective_date` 重跑，产物可对比、可回测

**裁决：硬需求（P0）。** 但"可复现"的合格线是**"输入可重放 + 产物可对比 + 回测可批量"**，不是逐字节一致（LLM 有温度，逐字节一致不现实，也不在工单骨架的原文要求里——04 骨架 L20 写的是"产物可对比、可回测"）。

**为什么（证据）**
- 北极星要"可靠"，可靠的前提是同一时点的判断可以被重跑复核；校准闭环（分层校准）要事后给判断打分，打分必须有可回到当时输入与产物的路径（06 定案 L43；说明书 L59）。
- 现有编排层已具备该形态：每次运行落 timestamped 目录与阶段清单（`orchestrator.py:464-494`，`run()` 在 L498）；断点续跑是明确的恢复语义（说明书 L102）。
- "价值买入、趋势卖出"要检验，唯一路径是回测（01 底稿 L83：具体阈值必须被定义、**回测（尊重 effective_date）**、事后打分）；回测 = 在多个历史 `effective_date` 上重跑同一套编排，没有可复现就没有回测。

**反驳面（什么情况下可以不是硬需求）**
- 如果系统只做一次性实时判断、永不回看、永不评分，可复现可降为"落盘留痕即可"。但这两条都被定稿否定：分层校准保留（06 定案 L43）、假说要回测（01 底稿 L83）。
- 如果"可靠"被重新定义成"读起来合理"而非"可复核"，可复现不再是硬需求——但那是另立北极星，不是本次基线。

**实时补采场景**：仍是硬需求，但强度略低一档——标准可以是"关键输入 + 各站产物落盘可重放、结论可对比"，不必保证两次跑字字相同；因为实时补采的材料本身带时间戳（说明书 L353 要求 `data_date`、`collected_at_utc`），只要落盘完整，事后可核对。
**历史回测场景**：**最硬，P0 中的 P0。** 同一 `effective_date` 两次跑出不可解释的不同结论，或同一天重跑拿不到相同输入窗口，整条回测结论作废。编排层必须暴露"按 `effective_date` 批量重跑"的能力，而不只是"按今天重跑"。

### Q2 · 隔离可事后证明：每站实际看到了什么，能落盘、能 grep 出来

**裁决：硬需求（P0）。** 这是系统目前**已经实现**的"公证层"能力（01 底稿 L30），也是层间隔离从"纸面承诺"变成"可审计事实"的唯一凭据。

**为什么（证据）**
- 说明书 L56：层间隔离"审计时用真实提示词逐层核对"；01 底稿 L30：每次运行把每站实际收到的完整提示词存盘，可事后 grep 核实。
- 代码侧：`orchestrator.py:487,492` 建 `prompt_audit` 目录；L2073/2083/2150 保存各站 prompt 文本与 JSON；L5520-5563 把每次尝试的 prompt/响应文件路径写进 stage_record。
- 三明治稿 R6（L52-55）进一步证明这种"可 grep"不是摆设：常设检查曾把"正确隔离"当病报警，靠的正是对落盘证据的机器断言——没有落盘，这类检查根本无处下口。
- 配餐单·四站 L12 的教训同源：瘦身可以删数值明细，但**不能删** `allowed_evidence_refs` 与 ref key，因为事后校验引用的合法性只能靠它们——隔离证明同样要求"实际发给了它什么"被保留。

**反驳面（什么情况下可以不是硬需求，或等价手段）**
- 若运行时引擎能从机制上锁死上下文（比如 schema 级白名单 + 引擎强制，想越权都做不到），"全文落盘 grep"可降级为"输入包 + 白名单 + 机器对账"——但"**每站实际看到什么可被证明**"这件事本身不能没有，只是证明载体可换。
- 若系统永远只有一条链、无跨层污染风险（没有 L1-L5 隔离、没有弱来源），可不要隔离证明——但这等于拆掉三明治，与 4.7 口径冲突（说明书 L370-380）。

**实时补采场景**：硬。实时补采是污染风险最高的场景（agent 出去采回新闻/网页，最易混进数据链）；必须能事后 grep 出每站到底拿到了什么、有没有 `event:` 前缀混进数据链（配餐单·余站 L13、L38）。
**历史回测场景**：硬且更重——回测的隔离证明同时是"未来信息没进层"的证据；grep 的对象从"跨层材料"扩大到"晚于 `effective_date` 的材料"（呼应 Q3）。

### Q3 · 时间窗口纪律：`effective_date` / 不得用未来信息

**裁决：硬需求（P0）。** 历史回测场景零容忍；实时补采场景同样硬（防的是"晚到/修订数据"与"补采回来的材料时间混装"）。DSH 有没有现成等价物属 B 面问题，本文件不预判；但**自造代价的账可以先算**：这不是改一行，而是"采集边界 + 组装断言 + 落盘证明"三件套，现有系统已实现，换编排器时必须整体保住。

**为什么（证据）**
- 01 底稿 L26：第一层数据链"信息窗口锁死（`effective_date`），事件材料永不进入任何一站"。
- `orchestrator.py:1162-1165`：`_effective_date()` 统一从 `data_date`/`backtest_date` 取，全链每站消息都带 `effective_date`；L1949-1968：事件历史总结若出现晚于 `effective_date` 的日期，直接判错（codex P1 防事后信息回流）。
- 说明书 L236：事件支线"不能引用晚于有效日期的信息"；L358：回测模式下"数据日期不超过回测日"是严格回测基线；`collector.py:291-306` 产出 `strict_backtest_invariants`、L619-655 产出 `backtest_data_boundaries`——数据层已把"不能证明回测日可见的数据"写入边界。
- 06 定案 L103：假说"未经回测，不作为决策依据"——回测有效的前提就是时间窗口纪律，违反即回测作废。

**反驳面（什么情况下可以不是硬需求）**
- 如果系统永远只跑实时、永不回测，"未来信息"在采集端天然不存在，可弱化为"给所有材料带 `data_date`/`collected_at_utc` 双时间戳即可"。但假说检验要求回测，这条退路被 01 底稿 L83 堵死。
- 如果第二层事件链完全不进任何判断（连 IA 都不进），事件侧的时间纪律可单独成规；但三明治定的是事件要进 IA 对质（三明治稿 L30），所以时间纪律必须贯穿到 IA。

**实时补采场景**：硬，但风险点不同——真正的未来信息不存在，风险是：agentic 补采回来的网页/新闻可能混入"预测类"材料、晚到的数据修订、或把今天看到的历史解释当事实。要求：所有材料双时间戳 + 事件卡时间断言（说明书 L236、L353）。
**历史回测场景**：最硬，零容忍。任何晚于回测日的材料进上下文 = 整条回测作废。自造代价最大项在"采集侧"（哪些数据回测日可见）+ "组装侧"（逐站断言输入材料日期）+ "证据侧"（落盘可查）。

### Q4 · 数据层 Python 生态（Wind / pandas / SEC）：能不能作为"被编排的工具"留在原处

**裁决：硬需求（P0）——必须能原样留在原处，不得以换编排器为由重写。** 这不是"最好保留"，而是"数字可独立重算、来源可追溯"（事实扎实支柱）的物理载体；重写数据层等于把系统最扎实的地基推倒，且没有任何北极星理由支持这么做。

**为什么（证据）**
- 说明书 L350-358：L4 估值主锚是 Wind NDX 指数级数据（`licensed_provider/Wind` 等来源等级），Damodaran ERP、WorldPERatio、yfinance/SEC/东财成分模型各有明确分工——整条数据发言权体系长在 Python 工具上。
- 说明书 L390-397：五层数据工具 `tools_L1.py` 至 `tools_L5.py`、`collector.py`、`checker.py` 等是 Python 模块；L409-423：编排链也是 Python。数据层与编排层的现接口是"同进程函数调用 + JSON 产物落盘"。
- 06 定案 L80-81：P5 瘦身的施工位置就是 `orchestrator.py` 两处打包——说明编排层与数据层在 Python 内是**可分离的**：编排层只组装材料包，数据层只生产数据。
- 配餐单·四站 L12：证据引用名的合法性校验"只看 ref key 是否存在，与 value 内容无关"——数据层产 value，编排层核 ref key，分工本来就不要求重写任何一边。

**反驳面（什么情况下可以不是硬需求）**
- 若未来数据源全部改成 HTTP API + JSON、Wind 终端/SEC 文件解析不再需要，Python 生态可逐步替换——但那是数据源演进，不是换编排器的理由，且当前没有任何定稿说要换数据层。
- 若 DSH 能原生跑 Python（子进程/沙箱/插件），"留在原处"与"被 DSH 编排"可同时成立，这是 B 面要查的衔接方式（04 骨架 B5），不影响 A 面结论。

**实时补采场景**：硬。实时 L4 主锚 Wind 快照（说明书 L354）必须在 Python 侧被调用；编排层只需"能触发、能读取、能校验"这些工具，不需要也不会因为换编排器而把 Wind 接入重写成别的语言。
**历史回测场景**：硬。回测数据纪律的实现就在 `collector.py`（L619-655 `backtest_data_boundaries`、L291-306 `strict_backtest_invariants`）——这正是"数据层 Python 生态"的一部分；编排层若绕过它自取数据，回测纪律立刻失效。

### Q5 · 治理纪律归属：弱来源不进主链、证据分级、发布闸门——哪些是编排层的责任、哪些是数据层的责任

**裁决：三层分责，但"执行与强制"主要落在编排层。** 一句话：**数据层负责"标注与生产"，编排层负责"配给与强制"，合约/schema 层负责"能锁死的锁死"。** 具体裁决：

| 纪律 | 数据层责任 | 编排层责任 | 合约/schema 层责任 |
|---|---|---|---|
| 弱来源不进主链 | 给事件打认识论标签（仅标题/未确认/来源等级；01 底稿 L28） | 默认 `allow_event_refs=False`，事件材料只发 IA 与展示位，机器断言第一层各站事件字段恒空（`packet_builder.py:365,379`；三明治稿 R3 L40-42、R6 L52-55） | 锁死"事件不得当 evidence_ref"的字段与检查 |
| 证据分级 | 给每条证据标 `permission_type`/`source_tier`/发言权（说明书 L342-343、L350-353） | 打包时保留这些标签、按站配给合法 ref 清单，不许模型自拼（配餐单·四站 L12、L29-41） | `PermissionType` 等 enum 落为合约（`contracts.py`） |
| 发布闸门 | DataIntegrity/数据边界报告（说明书 L58；`collector.py` 产物） | 链尾执行闸门：Schema Guard 纯代码站（说明书 L186-197）、终审 `quality_gate`、IA 的 `stance_echo` 逐字打回（配餐单·余站 L86） | 闸门判形状与身份，不判意思 |

**为什么（证据）**
- 说明书 L84："弱来源不进主链"是 `CLAUDE.md` 硬规矩在代码里的落地——落地位置在**组装/编排侧**（谁拿到什么材料）。
- 三明治稿 R3（L40-42）：`allow_event_refs` 默认 False 且全库无调用方打开（`packet_builder.py:365`）——这是编排层的隔离开关，不是数据层的。
- 说明书 L190-196：Schema Guard 是"唯一不是 AI 的一站"，由 `orchestrator.py` 的 `_run_schema_guard` 执行——发布闸门的机械部分住在编排器里。
- 配餐单·余站 L86：IA 的 `stance_echo` 与 `final_stance` 逐字全等、不等即整包打回——闸门在编排层执行。

**反驳面（什么情况下可以不是这样分）**
- 若证据分级能全部锁进 schema（enum 强制），"标注"就从数据层责任升级为合约层责任，编排层只管搬运——这是更好的方向（说明书 L285-293：轨道 > 导出 > 规矩），但当前只锁住了一部分，其余仍靠数据层标注 + 编排层传递。
- 若系统永不接入弱来源（第二层不建），"弱来源不进主链"闸门可退化为不存在；但第二层已定案要建（说明书 L240），所以该闸门必须有。
- 发布闸门若被移到独立于编排器的"公证层"服务，也可成立——但前提是它仍能在链尾强制执行；当前事实是它住在编排器里，A 面只要求"有且强制"，不要求"必须在哪个文件"。

**实时补采场景**：硬。实时场景弱来源最多、最易以"背景/触发因素"名义混入；编排层必须默认关死事件引用，且让第二层产物只进 IA 与报告展示位（三明治稿 R2 L34-38）。
**历史回测场景**：硬且更严。历史弱来源（当时的新闻）也必须按 `effective_date` 过滤后、带来源等级进 IA，不得把今天知道的历史叙事当数据证据注入回测（说明书 L236、L358）。

## 二、从北极星 + "价值买入、趋势卖出"推导编排层能力清单

> 说明：B1-B6 与 A 面 5 问同源，此处给裁决结论并补齐反驳与双场景；B7-B13 是 5 问之外的推导项。

### B1 · 短/中/长期三尺度独立覆盖 —— 硬需求（P0）

- **为什么**：北极星定稿明确"覆盖短、中、长期"（06 定案 L33）；论点建构与终审已按时间尺度产出判断与失效条件（说明书 L148、L218）。编排层必须在材料包与产物合约里把三个尺度分开承载，不能让"长期看好"吞掉"短期趋势破位"或反之。
- **反驳面**：若所有者只做单尺度（比如只做长期持有），可降级——但定稿北极星是三尺度，且"价值买入、趋势卖出"本身就是"长期价值 + 中短期趋势"的组合，必须分开。
- **实时补采**：硬，三个尺度各自要证据、姿态、失效条件。
- **历史回测**：硬，且三尺度要**分别评分**——短期判断几周后见分晓，长期判断几年后见分晓，编排层要把产物按尺度送到打分器。

### B2 · 可复现重跑与回测 —— 硬需求（P0）＝ Q1

- **为什么**：同 Q1。证据：04 骨架 L20；06 定案 L43；01 底稿 L83；`orchestrator.py:464-494`。
- **反驳面**：同 Q1——只有"永不回看、永不评分"时才可降级，而基线不允许。
- **实时补采**：硬，标准可放宽到"输入落盘 + 产物可对比"。
- **历史回测**：最硬，必须支持按 `effective_date` 批量重跑。

### B3 · 隔离可事后证明 —— 硬需求（P0）＝ Q2

- **为什么**：同 Q2。证据：01 底稿 L30；说明书 L56；`orchestrator.py:487,492,2073-2150,5520-5563`。
- **反驳面**：可用"引擎强制白名单 + 机器对账"部分替代全文 grep，但"可证明"本身不可省。
- **实时补采**：硬，防补采材料污染数据链。
- **历史回测**：硬，隔离证明同时是"无未来信息"证据。

### B4 · `effective_date` 时间窗口全链强制 —— 硬需求（P0）＝ Q3

- **为什么**：同 Q3。证据：01 底稿 L26；`orchestrator.py:1162-1165,1949-1968`；说明书 L236、L358；`collector.py:291-306,619-655`。
- **反驳面**：只跑实时永不回测时，可弱化为"双时间戳纪律"；基线不允许。
- **实时补采**：硬，防晚到/修订数据与补采材料时间混装。
- **历史回测**：最硬，零容忍，违反即回测作废。

### B5 · Python 数据层原样可编排 —— 硬需求（P0）＝ Q4

- **为什么**：同 Q4。证据：说明书 L350-358、L390-397；06 定案 L80-81。
- **反驳面**：数据源全部 HTTP 化后 Python 生态可演进，但那是数据源演进，不是换编排器的理由。
- **实时补采**：硬，Wind 实时主锚必须留在 Python 侧被调用。
- **历史回测**：硬，回测边界逻辑在 `collector.py`，不可绕过。

### B6 · 治理纪律强制点 —— 硬需求（P0）＝ Q5

- **为什么**：同 Q5。证据：`packet_builder.py:365,379`；说明书 L84、L186-197；三明治稿 R3/R6；配餐单·余站 L86。
- **反驳面**：弱来源永不接入时"不进主链"闸门可省；发布闸门可移到独立公证层，但"有且强制"不变。
- **实时补采**：硬，弱来源最多、最易混入。
- **历史回测**：硬，弱来源历史材料同样要按 `effective_date` 过滤。

### B7 · 证据引用身份与白名单机械校验 —— 硬需求（P0）

- **为什么**：事实扎实支柱要求"数字可独立重算、来源可追溯"（01 底稿 L40）；Schema Guard 是唯一非 AI 站，直接扫描合法证据编号逐条比对（说明书 L190-192）；配餐单·四站 L12 裁定瘦身绝不能删 `allowed_evidence_refs` 与 ref key；"自拼 parent#field"被列为禁止（配餐单·余站 L68）。
- **反驳面**：若放弃逐条引用审计、允许自由文本结论，可降级——但发布闸门与事实扎实支柱都不允许（说明书 L302：索引缺失产出必须标记"不可作发布依据"）。
- **实时补采**：硬，模型只能引用白名单内的证据身份。
- **历史回测**：硬，且白名单本身要按回测日裁剪——晚于 `effective_date` 才存在的证据身份不得出现在清单里。

### B8 · 证据面均衡与冲突保留 —— 硬需求（P0）

- **为什么**：三支柱"证据面均衡"原样保留（06 定案 L43）；正反双方拿同一份证据菜单、代码层面做不出偏科（说明书 L57）；"冲突是资产"、conflicts 字段不允许为空（说明书 L124、L306-315）；critic/risk 分料与论证盲是对均衡的加固（06 定案 L84-95；配餐单·四站 L44-58）。
- **反驳面**：若系统定位改成"只给所有者一个方向参考"，均衡可不要——但那是另一套系统，且与定稿北极星"可靠"冲突。
- **实时补采**：硬，正反同菜单、反方在主论点前先跑（说明书 L136-138）。
- **历史回测**：硬，且均衡菜单要按回测日裁剪——不能把后来才知道的证据塞给正方。

### B9 · 判断与决策分离（负向硬需求：不建翻译层、不自动下单）—— 硬需求（P0，边界型）

- **为什么**：01 底稿 L43 列"判断与决策分离"为不重议原则；06 定案 L99-107 裁定翻译层**不建**，假想只登记一句话；说明书 L364 明确"报告给人，人自己定"是有意识接受的缺口。
- **反驳面**：若所有者未来明确要求自动执行/信号层，需先改北极星与原则，再谈编排层能力；当前不是。
- **实时补采**：硬，编排层产出判断书，不产出下单指令。
- **历史回测**：硬，"买卖决策"只作为**被评估对象**（假说回测），不得成为系统自动执行动作。

### B10 · 失败软着陆、降级留痕、断点续跑 —— 硬需求（P1）

- **为什么**：说明书 L102（断点续跑）、L140（反方降级事故：降级了却没进终审质量闸门，已立案——教训是"降级必须留痕"）、L210（修订者软着陆 + `degraded_fallback` 显式标记）、L238（事件支线失败留白不硬凑）；配餐单·余站 L46（受控调查失败要占位进 IA）。
- **反驳面**：若每次运行足够便宜、允许失败即整链重来，断点续跑可省；但"降级/失败必须留痕、不得静默通过"不可省（发布闸门的一部分）。
- **实时补采**：硬，单站失败不得静默产出可发布结论。
- **历史回测**：硬且更重——批量回测几十个历史日期，一个日期失败不应全灭，断点续跑是批量回测的经济前提。

### B11 · 按站配餐与成本可控 —— 硬需求（P1）

- **为什么**：06 定案 L76-82 裁定反方/论点输入瘦身是"全链最大的一笔浪费"；配餐单·四站 L65-70 实测账（瘦身已把两站从约 56 万压到约 14-16 万字符）；说明书 L254-275 真实结算单显示反方/论点占全链 4 成以上。编排层必须按站裁剪输入，但裁剪**不得删证据身份与校验所需字段**（配餐单·四站 L12）。
- **反驳面**：若 token 成本趋零且上下文窗口无限，成本压力下降；但"模型注意力有限"（说明书 L285）与上下文上限仍使按站配餐有意义。可降为 P2 当成本不再约束。
- **实时补采**：硬，每跑一次都是真金白银。
- **历史回测**：硬，批量回测把成本放大 N 倍，按站配餐是回测可行性的经济前提。

### B12 · 双模运行（实时 / 回测）+ 假说可回测、可事后打分 —— 硬需求（P1）

- **为什么**：假想登记句"未经回测，不作为决策依据"（06 定案 L103）；01 底稿 L83 要求"黄金坑/趋势破"阈值必须被定义、回测（尊重 `effective_date`）、事后打分；说明书 L59 打分回环已就位但零次真实运行。编排层必须让**同一套站点逻辑**在实时与回测两种模式下都能跑，并把产物接到打分器。
- **反驳面**：若所有者放弃检验该假说、只当口号，系统可不建假说实验；但北极星"比长期持有更好"本身需要回测/记账才能证明，所以至少打分接口要有。
- **实时补采**：实时模式是回测的镜像——实时判断要能被未来打分，所以两模式必须共享同一套产物合约。
- **历史回测**：本条的主场；回测模式必须与实时模式同构，否则回测结论不能外推到实时。

### B13 · 第二层 agentic 补采的隔离接口与来源标签词表 —— 硬需求（P2）

- **为什么**：说明书 L240 已定 T48 混合形态（确定性底账 + agentic 补采三档，外部 harness 选型**留到原型之后**）；三明治稿 L108 同口径；配餐单·余站 L16 要求来源等级词表与弱来源分档（现无词表）。编排层现在不必须实现补采，但必须给第二层产物留"只进 IA/展示位"的接口，不能堵死。
- **反驳面**：若第二层永不施工，本条可无限期挂起；但 T48 已定案，接口预留是既定义务。
- **实时补采**：补采的主场；接口与标签词表是补采材料进入 IA 的前提。
- **历史回测**：agentic 补采默认关闭或严格按 `effective_date` 过滤（说明书 L358）；接口要能整体关闭。
