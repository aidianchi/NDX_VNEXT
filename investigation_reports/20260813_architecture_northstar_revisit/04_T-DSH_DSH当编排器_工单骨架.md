# T-DSH 工单骨架 · 是否用 DeepSeek Harness 当编排器

> 状态：**骨架，未启动。** 前置依赖未满足（P2 北极星、P5 编排结构尚未定），等六问验收辩论出结论后再填肉、再开工。
> 性质：这是**架构第一性原理问题，不是技术细节**，不可草率，更不可由单方下结论。

## 为什么（一句话）

系统的编排层现在是一条固定的 Python 链（`orchestrator.py`）；所有者怀疑它"死板"，想判断 DSH 能否作为（全部或部分）编排器、吸收现有架构的优点。但此问不能空对空——必须先知道"架构到底需要什么"（A 面）与"DSH 到底是什么"（B 面）。

## 前置依赖（不满足则不开工）

- **P2（目的 / 北极星）已定**：知道"可靠"之外还要不要"可测量变好"、系统的价值用什么衡量。
- **P5（编排结构）已定**：知道治理链该保持 / 合并 / 裁撤、成本账是多少。
- 两者结论是 A 面的输入；没有它们，A 面就是空转。

## A 面 · 架构到底需要什么（第一性原理）

抛开 AI 后加进文档的目的（"可审计""可测量"等），只按**定下来的北极星 + 所有者的"价值买入、趋势卖出"假想**，推导编排层**必须**满足的能力清单。至少逐条裁决：

1. **可复现**：同一 `effective_date` 重跑，产物可对比、可回测。这是不是硬需求？在"实时补采"与"历史回测"两种场景下**分别**回答。
2. **隔离可事后证明**：每站实际看到了什么，能落盘、能 grep 出来。这是不是硬需求？有没有别的等价手段？
3. **时间窗口纪律**：`effective_date` / 不得用未来信息。DSH 这类运行时有没有现成等价物？没有的话自造代价多大？
4. **数据层 Python 生态**（Wind / pandas / SEC）：能不能作为"被编排的工具"留在原处，而不必重写？
5. **治理纪律归属**：弱来源不进主链、证据分级、发布闸门——哪些是编排层的责任、哪些是数据层的责任？

## B 面 · DSH 到底是什么（读源码 + 自我剖析）

深入读 DSH 的代码与文档，结合其运行机制，回答：

1. 它的编排模型是什么（插件 / 服务 / 事件 / 子代理 / 工作流 / 目标循环），各自的隔离边界与可复现性如何？
2. 它的"子代理上下文隔离"与现系统的"落盘-grep 隔离证明"，是同一类保证吗？**差在哪？**
3. 它有没有 `effective_date` / 回测 / 时间窗口的概念？没有的话，补上要动它哪一层、代价多大？
4. 它是"会话式运行时"还是"可重复的批处理管线"？对"一键重跑、产物落 timestamped 目录、事后审计"这个需求，它原生支持到什么程度？
5. 它的宿主语言（Node.js）与现系统的 Python 数据层，如何衔接（shell out / 重写 / 别的桥）？

## A × B 对质 → 初步结论

- 逐条把 A 面的"必须能力"对上 B 面的"DSH 能 / 不能提供"，分出四档：**原生满足 / 可等价达成 / 需自造 / 根本冲突**。
- 结论只允许落在三种之一，且带证据链：① DSH 可当（全部或部分）编排器；② DSH 只适合某层（如第二层 agentic 补采）；③ 不该用 DSH。
- 每个结论必须附**失效条件**（出现什么会推翻它）。

## 验收标准

- A 面能力清单逐条有"是不是硬需求"的裁决与理由（含反驳）。
- B 面每条有源码 / 文档证据（文件路径或可复跑命令），不靠印象。
- A×B 对照表完整；结论带失效条件。
- 至少一份**外部 AI 的红队意见**（见红线第一条）。

## 红线

1. 此问的结论**不得由"运行在 DSH 上的 AI"单独下**——它对 DSH 有天然立场；必须引入外部 AI 红队，像六问一样对质。

3. 技术路线结论**不得先于**北极星结论（前置依赖未满足，此工单就是空转）。
