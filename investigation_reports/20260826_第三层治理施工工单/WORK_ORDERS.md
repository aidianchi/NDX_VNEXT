## W1 · Brief 标题换人话（一行级改动，最先做）

**病灶**：终审每轮都产出给人看的一句话结论 `reader_final.one_liner`（质量实测良好），但 Brief 大标题优先用 `final_stance`（给系统看的姿态句，术语句），one_liner 只是空缺备胎。

**证据**：
- `src/agent_analysis/vnext_reporter.py:2388`：`<h1>{_escape(final.get('final_stance') or reader.get('one_liner') or '本轮判断')}</h1>`——final_stance 优先。
- 实测（20260826_124855 run）：one_liner 原文"等NVDA财报和697-698支撑选择方向"在 `output/reports/vnext_brief_20260826_1248.html` 全文检索 **-1**（从未出现）；而 H1 是 final_stance 的密术语长句。
- 对照旧例：07-19 Brief 好看只是那轮 final_stance 碰巧写得像人话（`20260719_130534/final_adjudication.json` 的 final_stance 与旧 Brief H1 逐字一致）——运气不是机制。

**改法**：
- 2388 行优先级反转：H1 = `one_liner`，为空回退 `final_stance`，再回退"本轮判断"。
- final_stance 不丢弃：降级为大标题旁的小标签（badge/副行），深度不减。

**验收**：
1. 先红后绿单测：两字段同在 → H1=one_liner 且页面含 final_stance 标签；one_liner 缺失 → 回退 final_stance。
2. 用 20260826_124855 run 的落盘产物重渲染 Brief，人工确认 H1 是人话句。

**认错条件**：无风险项；若发现 Brief 有多处门面（workbench/console 各自渲染），本件只动 Brief，其余记入 W5 后续（⑦ 门面移交时统一）。

## W4 · 抗诉通道（小施工，零新增 AI 调用）

**病灶**：研究架上对账通过的核实事实（已非弱来源）与数据判决姿态正面冲突时，只能埋在正文 tension 记录里；PC-27 只盖事件卡挑战（challenged_by_data），研究架事实挑战无升级通道。

**老板裁定口径（2026-08-26）**："该抗诉的抗诉，不该抗诉的时候不抗诉"——三条件**同时满足**才亮红灯：
1. 材料是研究架上**对账通过（verified）**的事实卡；
2. 与数据判决姿态**正面冲突**（不是擦边、不是同向）；
3. **实质矛盾**（IA 判定，非噪声）。
互相印证/互相补充的走正常对质记录通道，不亮灯、不占门面。

**改法**：
- IA 产物侧：核实事实冲突行进 conflict_matrix（或新增 objection 字段——设计时二选一，倾向复用 conflict_matrix 减少契约面）。
- 常设检查：扩出 PC-28（或按 PC-27 模式扩口径）——"研究架 verified 事实挑战数据姿态"非空即亮灯。**新增常设检查的所有者批准已含在老板对 W4 的批准内（2026-08-26 23:47），WORK_LOG 登记时写明此依据。**
- 展示侧：Brief/综合报告第一屏渲染红灯异议块（置顶、显眼、带来源引用），文案明示"这不是系统故障，是经核实的外部事实与数据判断正面冲突，需老板阅读裁决"（沿用 PC-27 的 message 风格）。
- **离线校准（上线前必做）**：拿最近 ≥6 个真实 run 的 `integrated_synthesis_report.json` 离线跑判定逻辑，统计亮灯频率。天天亮 = 刻度错，调刻度后重来（PC-27 的狼来了教训，08-19 有案）；一次不亮也正常（没冲突就是没冲突）。

**验收**：先红后绿测试（verified+正面冲突 fixture → 灯亮；同向/擦边/未对账 fixture → 不亮）；离线校准报告落盘本目录；全量绿。

**认错条件**：若离线校准发现 flash 写的 conflict_matrix 行噪声太大分不清真冲突，降级方案 = 先只做"机器判定"（代码比对 verified 事实方向与 final_stance 方向标签），不让模型自己判"实质矛盾"——宁可灯少亮，不可天天红。

## W5 · 裁决批评者（中等施工，正反合成型）

**病灶**：IA 单次调用写综合报告，无反方、无批评、无修订——全系统治理最薄的产物是老板直接读的最终产物（治理深度与影响力倒挂）。

**改法**（参照主链 critic 站既有模式，`src/agent_analysis/prompts/critic.md` + contracts.py 注册 + 分料纪律）：
- 管线内两步：IA **草稿** → **裁决批评者**（专挑：逻辑跳步／把事件假设性影响写成既成因果／抹平冲突与和稀泥／数字无出处／引用越权）→ IA **定稿**必须逐条回应（接受修正 / 驳回带理由）。
- **分料**：批评者拿 IA 草稿 + 与 IA 同输入面的许可白名单派生材料，**不给额外原始数据**——防它变成第四方数据源。
- **机械字段**代码装配（编号/时间戳/引用键），批评与回应全部落盘（建议新 artifact `integrated_adjudication_critique.json`），可审计。
- **兜底**：批评者两次失败 → IA 原稿直接放行并显式标注 `critic_degraded`（不阻断 run，参照修订者软着陆先例——但注意性质是"标注放行"不是"退回原稿"，因为本站没有上游原稿概念）。
- token 进 `token_usage`，模型路由沿用现有 config（flash 优先）。
- 文档同批：说明书 2.11 加一段、第五节模块地图加一行、架构图第三层加一站（维护义务）。

**成本**：每次 run +1~2 次调用（参照终审约 7 万 token/次的量级）。

**验收**：先红后绿（含批评者失败兜底路径）；token_usage 可见新增两站；真实 run 一次验证批评-回应链完整落盘；全量 + docs 绿。

**认错条件**：若实测批评者全是走过场的套话（连续 N 次挑不出真问题），停下来报告老板——那是提示词或分料病，不是加轮数能解决的；参照老板 08-25 两问（先怀疑提示词蠢或闸门死板，再怀疑模型）。

## W6 · 底账修真缺口（采集工程，可与 W4/W5 并行）

**病灶与证据**（20260826_124855 run，63 条实测）：真缺口两处 + 一个设计缺口：
- a. **Yahoo 正文抓取成功率 7/16**（44%）：查失败原因（反爬/超时/格式），提升成功率；抓不到的如实标注，不硬造。
- b. **Reddit 正文 0/4**：评估抓正文的可行性与价值（社媒叙事档的正文价值 vs 工程成本）；可行则接，不可行则保持"仅标题"并把语义在文档写清（结构性无正文）。
- c. **关键词表写死**：`src/news_event_ledger.py:177-215` 的 HIGH_RELEVANCE_KEYWORDS / BODY_FETCH_KEYWORDS 是静态表，新主题不自动进池——这是底账真正的"随意性"风险（焦距固定）。

**改法**：
- a/b 直接施工，用前后对照表（抓取成功率数字）说话。
- c **本工单只到设计稿为止**：出"词表活化机制"设计稿（候选方向：出题官/巡逻/data_gaps 发现的新主题 → 候选词清单 → **老板圈定入表**——词表是采集边界，归老板，不做全自动），落盘本目录 `W6c_词表活化设计稿.md`，等老板拍板后再施工。

**验收**：a/b 有前后对照数字；c 交设计稿即算本工单内完成（施工另批）。

**认错条件**：抓取类工程遇网站改版/反爬升级导致成功率不升反降，如实记录并给老板两个选项（换源/放弃该源），不无限死磕。
