## 三、外包可行性评估：哪些能交、哪些不能

### 能交给便宜 AI 的（机械、边界清、验收可机器化）

| 任务 | 为什么适合 | 验收方式 |
|---|---|---|
| 阶段 B 全部 20 项常设检查 | 纯机械：sha256 比对、集合包含、存在性检查，判据已在 T47 §8 写死 | 每项：红灯测试（先证假阳性会报警）+ 全量 pytest 绿 |
| C2 终审输入改造 | 拍板已定，纯装配：把修订稿+修订说明接进 final 输入 + "摘要以实物为准"校验 | 构造测试：final 输入含 revised 字段；自称添加的字段必须在实物存在 |
| C3 layer_facts 去预置 | 拍板倾向已定（路线二），改动是删供给不是加逻辑 | 五层 payload 无 state 键 + L1-L5 合约测试适配 |
| C5 调查材料打包修复 | 截断/立场字段/失败占位都是形状问题 | 材料 JSON 闭合 + 立场词扫描为零 + 失败调查有占位记录 |
| T42 余三处 | 身份/存在性比对，不判意思 | 各配红灯测试 |
| 文档格式化更新 | 有明确模板时 | 我逐字复核 |

### 不能外包的（应然判断 / 碰红线 / 需要全链路视野）

| 任务 | 为什么不能 |
|---|---|
| 阶段 A 配餐单本身 | "该给什么"是应然判断——拍板原话"留给所有者拍板，不外包给 AI"；我可以起草，但每条要你过 |
| C1 的分料设计细化 | 拍板给了方向，"各站视角小块"具体切什么是判断活 |
| C4 事件链接法 | 卡在"两说 1"（治理链楼层口径）未裁；且碰三层边界红线，接错站就是架构事故 |
| 任何碰 evidence_ref 合法性、发布闸门、effective_date、L1-L5 隔离的改动 | 常驻边界，根线程必须自己判断（AGENTS.md 调度纪律原文） |
| 阶段 F T38 设计 | 架构级设计，七路审计已演示过"三路严重度报高被汇总层改判"的教训 |
| WORK_LOG / 现在.md 的状态裁决 | 状态只写一处，关单措辞是纪律活 |

### 必须给便宜 AI 套上的护栏（本项目两次施工方事故换来的教训）

1. **工单制**：每单写死——可碰的文件清单、验收标准、禁止事项；范围外一个字不许动。
2. **红灯测试先行**：先写一个"修复前必然红"的测试，证明病真实存在，再施工。
3. **HEAD 是不可变基线**：验收时拿 `git diff HEAD` 逐行比对——2026-07-31 和 08-05 各有一次施工方误删/误归因，都是靠 HEAD 比对抓出来的；施工方对"损伤是否自己造成"的自辩不可采信。
4. **交付即复核**：每单回来我做只读复核 + 全量测试（当前基线 1077 项量级），红线相关行我逐行读。
5. **不许它记账**：WORK_LOG/现在.md/工单状态行由验收后统一记，施工方不碰状态文件。
