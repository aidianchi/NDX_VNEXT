## 对账口径（每站"声明"与"供给"按什么形态提取）

各站提示词的"许可"形态不同，机械提取前先按形态归类。本次对账使用三种形态：

- **形态 A · ref/材料编号清单**：指令里有机器可提的许可清单（如 `allowed_evidence_refs`、`[M#]` 材料编号、`ref_authority`、`core_allowed`），供给是提示词材料区里真实出现的 ref/编号。对账 = 两个集合的差集 + 空头检查（声明条目在供给里为 null/占位/空数组）。
- **形态 B · 键/字段清单**：指令点名要读、要回答的 JSON 键名/文件路径/字段名（如"输入边界"声明、任务书点名的 packet 键），供给是该站材料 JSON 里真实存在的键路径。对账 = 声明键 vs 供给键的差集 + null/空检查。
- **形态 C · 无机器可提清单**：指令只给定性要求（"依据下面材料"），没有枚举清单；只能人工判读材料与任务的对得上与否，在对账表里标注"人工判读"。

提取手段与近似性声明：

- 实际执行：所有"声明 vs 供给"的集合比较全部走 `full/` 原文 Runtime Input 的 JSON 整解析后做精确集合运算（脚本见各节），未使用正则近似提取；正则仅用于定位提示词章节边界（如 `## Runtime Input` 起止行）。
- "空头"判定标准：声明清单条目在供给材料中对应值为 `null`、`"unknown"`、`"待定"`、`[]`、`{}`、或仅出现键名而无数值。
- 投影截断提示词（manifest 中 projection_ratio < 1 的站），凡涉及"供给里有没有某键"的结论，一律到 `context_spread/full/` 原文核验，不以投影为准。
- 数字（条数、占比）一律由 /tmp 下可复跑脚本产出，输出原样贴入报告。
