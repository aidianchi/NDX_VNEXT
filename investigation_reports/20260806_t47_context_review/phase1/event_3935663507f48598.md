## 发现清单

### 发现 1：输出契约在站内以三种形态重复出现，合计约 2,183 字符（43.9%）

同一输出形状出现三次：

- (a) Runtime Input 内嵌 `output_contract` JSON 示例（prompt 第 71–103 行，907 字符，18.2%），带语义占位注释（如 `"fact_summary": "只写材料事实"`、`"upgrade_candidate": false`）。
- (b) `## 输出字段规格` 正式规格（第 111–123 行，905 字符，18.2%），逐字段标注必填/可选与类型。
- (c) `## Response Rules` 第 128 行再次完整列出 12 个顶层字段名，并在第 129 行声明形状优先级。

证据：

```
$ sed -n '125,130p' attempt_1.prompt.txt
## Response Rules
- 只返回一个 JSON 对象。
- 不要使用 markdown code fence。
- JSON 顶层字段必须匹配: event_id, fact_summary, interpretation, entities, event_type, mechanism_hypothesis, supports_hypotheses, refutes_hypotheses, limitations, needs_data_confirmation, upgrade_candidate, passport。
- 字段的**形状**（对象 / 数组 / 标量、是否可为 null）以上面「输出字段规格」为准；正文里的示例只解释语义，形状冲突时以规格为准。
- 不要编造新的外部数据源，只能使用输入中的信息。
```

事实：第 129 行"形状冲突时以规格为准"一句，说明提示词自身承认 (a) 与 (b) 两处规格可能冲突并预设了优先级；三处合计 2,183 字符，占全文 43.9%，与"数据材料"（event_material 554 字符）的比例约 3.9:1。
