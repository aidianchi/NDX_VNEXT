# T45/C17 比较报告（老板版）：要不要重建？A / A′ / B 选哪个？

> 本报告严格按 `investigation_reports/20260816_T45_comparison/00_预注册决策规则.md`（调研开始前冻结并提交，git `c66e405`）推结论；调研期间规则未改。

## 结论（先给老板）

1. **不建议重建。** 上次体检查出的五个历史缺陷，没有一条的根因在"运行框架"这一层——全部在我们自己的拼装代码、数据层、合约层和产物层。按冻结规则，重建路线到此终止（第 3/4 问按规则不展开，不是偷懒）。
2. **建议留在现架构，选 A′**：代码先把证据按每站职责分好档，再在每站输出表里加一个**必填的"我还缺哪几条材料"字段**（只能从系统给出的编号清单里勾选）。零新增往返、零新增失败面，把过去"模型靠自觉在散文里说缺料"变成"机制强制报告缺料"。
3. **不建议 B**（让模型自己跑腿取材料）：DeepSeek 思考模式当前不支持"强制调用工具"的开关；官方明确 `auto` 模式下模型可以"不取材料直接答题"；强制调用实验有 40–60% 无效 JSON 记录；循环多轮对缓存不友好。"B 能省 20% 成本"没有任何可测证据。按冻结规则 B 的三道门槛一道都过不了。
4. 全部外部事实带 URL + 日期，全部代码事实带 `文件:行号`；拿不到证据的一律写"未证实"。

## 二、第 1 问：三种做法各自的可审计性所得，值不值代价？

### 三变体一句话
- **A（代码侧检索）**：组装提示词之前，代码按"该站自己声明的问题"做相关性排序、取前 K 条。审计所得 = "代码筛了哪 K 条、依据、排除了哪些"。
- **A′（代码侧深度分档 + 必填缺料回报）**：A 的基础上，在站点**输出表**里加必填字段 `unmet_information_needs`（ref 枚举），模型物理上只能勾系统给过的编号。审计所得 = A 的筛选留痕 + **事后缺料回报**，可直接反哺筛选器。
- **B（模型侧按需取用）**：模型自己发起取用调用，单次调用改成循环。审计所得 = 模型**事前**主动要了哪几条。

### 关键事实
- A 目前**没有实现**：仓库现有裁剪只是"按黑名单删字段 + 压缩超长审计明细"，不是相关性 top-K（`src/agent_analysis/orchestrator.py:7128-7265`）。
- A′ 在现有系统里**全部零件齐备**：
  - 必填 + 枚举 = pydantic `Field(..., ...)` + `Literal`，现有契约已有先例（`src/agent_analysis/contracts.py:2106-2109`）；
  - 新字段自动进提示词（`src/agent_analysis/orchestrator.py:7096-7126`）；
  - **已有"给输出 schema 动态注入本轮真实编号枚举"的生产先例**：thesis/reviser 的 `conflict_id` 就是这么做的（`src/agent_analysis/orchestrator.py:4664-4700`），模型打不出清单外的值；
  - 严格模式 sanitizer 强制 `required` 全覆盖且支持 enum（`src/agent_analysis/llm_engine.py:126-157`）；
  - `_run_stage` 每次 attempt 只调一次模型、无工具结果回灌 → A′ 相对 A **零新增往返、零新增失败面**（`src/agent_analysis/orchestrator.py:5671`；`llm_engine.py:616-622`）。
- 必须诚实说明一个限定：严格模式只在"模型调用工具"时生效；`tool_choice="auto"` 下模型可以不调用工具直接返回文本，此时靠 pydantic 必填校验 + 重试兜底（`llm_engine.py:566-622`）。所以 A′ 是"工具被调用时 schema 强制 + 任何路径 pydantic 兜底"，不是绝对强制——但相对 A 没有新增任何失败面。
- 成本现实：最近真实 run 全量输入 **963,419 token**（L1-L5 占 45.7%，治理四站占 30.4%）；治理四站的 `key_evidence_refs` 四份**逐字节相同**（116,150 字符 ×4）；四站提示词相似度 95.2–97.8%，但公共前缀只有约 0.16%，前缀缓存基本吃不到（证据包 1.4，均为本机复算）。

**按规则第一条（A′ 优先于 A）**：A′ 能满足"放进现有输出表、不加往返、不新增失败面"三个条件，且已有同款工程先例 → **最终建议落在 A′，不落在 A**。

## 三、第 2 问：B 的循环化新增失败面有多大？

**答案：当前 DeepSeek V4 上，B 的失败面无法压到"可忽略"，且三道规则门槛全过不了。**

| 规则门槛 | 证据 | 判定 |
|---|---|---|
| (a) "事前取用意图"的审计价值不可被 A′ 事后回报替代 | 没有任何论文/产品文档直接证明这个强命题——**未证实**；Anthropic 上下文工程明确"预筛 + 按需取用"是混合策略而非唯一正解；S2G-RAG（ACL 2026）证明"事后结构化缺口 → 驱动下一轮检索"是成熟组件，与 A′ 同构 | **不满足** |
| (b) `auto` 下模型不取工具的概率能被约束到可忽略 | DeepSeek 官方：`auto` 允许"不调用工具、直接生成消息"，且不公布概率；**思考模式下 `tool_choice="required"` 和指定函数名都被 400 拒绝**（GitHub issue #1376，2026-05-30，open）；强制命名时 v4-flash 长 prompt 下 40–60% 无效 JSON（issue #1541，2026-08-02） | **不满足** |
| (c) B 比全量推送省 ≥20% | 官方缓存要求"完整匹配前缀单元"；Azure 多轮工具调用实测 cached_tokens 出现全 0/停增/首轮更高三种不稳定（Microsoft Q&A，2026-08-08）；Hermes-agent 实测工具 schema 占输入账单约 70%（2026-05-06）；本仓库 `prompt_cache_hit_tokens` 尚无真实命中数据 | **无证据支持，不满足** |
| (d) 不破坏五层隔离与字节级审计 | 现有 `prompt_audit` 管道完备（`orchestrator.py:5848-5894`），但 B 需要新增每轮工具回灌审计，能否等价落盘取决于设计——自动满足**未证实** | 可设计，但规则 2 已因 (a)(b)(c) 失败 |

**结论：不建议 B。** B 不是方向错了，而是当前 DeepSeek 模型形态（思考模式 + `tool_choice` 限制 + 缓存行为）给不了它一个可接受的失败边界。
