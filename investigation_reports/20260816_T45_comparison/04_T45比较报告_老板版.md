## 一、先解释"预注册决策规则"是什么

### 一句话版本

**动手查证之前，先把"什么证据下我给什么结论"白纸黑字写死；查证过程中，一个字都不许改。**

### 打个比方

好比医生做检查。医生不能等报告出来之后，再临时定"指标到多少算有病"——那样他总能定出一个让自己想下的结论的标准。正确做法是：**先写清楚"指标超过 X 就建议手术，没超过就不建议"，再去做检查，拿到结果照标准套。**

T45 就是按这个规矩干的：先写标准、锁进档案 → 再查证据 → 查完拿证据套标准 → 套出什么结论就是什么结论。全程标准没改过一个字，事后也查得到"确实没改"。

### 这份标准具体写了什么

一共四类规矩：

1. **第 0 问怎么判**（最关键的一条）：把五个老毛病挨个查病根——病根落在"总装线"（那套把各 AI 岗位组织起来跑的通用骨架）上的有几个？**数出 0 个 → 不建议换框架**，后面两个"评估新框架"的问题按规则直接停，不用查；数出 ≥1 个 → 才继续往下查。
2. **什么情况下才允许说"重建"**：必须五条全满足——至少一个病根在总装线；新框架那些"自动往 AI 脑子里塞东西"的功能都能关掉（要有证据，不许说"应该能关"）；关完它还剩至少三样真本事；换过去后仍能"逐字查账"；迁移成本不超过留在原地方案的两倍。
3. **A / A′ / B 怎么选**：**A′ 优先于 A**——只要 A′ 能塞进现有交卷表、不多跑一趟、不添新故障点，就不许只推荐 A；**B 要过四道高门槛**，一道不过就不许选。
4. **报告纪律**：只许给一个主结论，不许摆三个"都行"；外部说法必须带来源和日期；自家代码的事实必须带位置、能复核；拿不到证据的写"未证实"；查证期间不许改规则。

### 为什么要这么麻烦

就一个目的：**防止自己骗自己。** 人查事之前心里往往已有倾向，不先定标准，就容易"先想好结论、再挑支持它的证据"。标准先锁死，结论就是"规则 + 证据"算出来的——谁拿同一套规则、同一批证据，都得同一个答案。规则没覆盖的地方，只能老实写"未覆盖"，不许偷偷补。

## 二、T45 到底在查什么

### 背景

T45 是这次调研任务的编号（和 C17 是同一件事）。它**只出报告、不动代码、没花一分 API 钱**。

由来：之前给系统做全屋体检，查出五个历史老毛病。于是有个根本问题要回答：**这五个毛病，是不是"房子骨架"不行，要不要推倒重盖？如果不重盖，给 AI 送材料的方式，三种方案选哪个？**

### 五个老毛病，翻译成人话

| 毛病 | 人话 |
|---|---|
| 幽灵许可 | 允许引用的 26 条材料里 20 条有名无实：许可单和实际送的材料是两张皮，各写各的 |
| 预算截断 | 调查员声明要 4 条材料，唯一带数字的排第 4；系统按"只给 3 条"一刀切，第 4 条被默默扔掉 |
| 用实时数据冒充历史 | 回测该用"当时"的数，有个兜底数据源拿今天的数冒充 |
| 两个书房开不出细账 | 编号 L3、L5 的两个书房数据没登记，永远只能整包引用，不能按材料条目精确引用 |
| 严格模式没留痕 | 开了"严格交卷"模式，跑完的档案里却看不出开没开 |

**注意：查病根 ≠ 修病。** 这五个里，三个已在别的批次修好，两个还挂在账上；修没修都不影响今天的判断——因为问题不是"要不要修"，是"换框架能不能治"。

### 三种给料方案，翻译成人话

- **A：管家配菜。** AI 上岗前，代码按"这个岗位自己说关心什么"把材料排好序，只送最要紧的前 K 条，并记下"送了哪几条、凭什么、扔了哪几条"。
- **A′：管家配菜 + 饭后必答题。** 在 A 的基础上，每个岗位交卷时必须填一栏"我还缺哪几条材料"，只能从系统这轮给过的编号里勾，不能瞎写。
- **B：让 AI 自己跑腿。** AI 想要什么材料，自己发出指令去材料库取；一趟取完变成多趟来回。留的账是"它事前主动要了什么"。

### 查出来的答案：三问三答

**第一问：五个毛病的病根，在不在"总装线"上？**

答：**0 个。** 五个病根分别落在我们自己的拼装代码、数据采集、合约登记、产物留痕上。换外面的框架，这五个病一个都不会自动好，都得自己动手改。按预注册规则，数字是 0 → **不重建**，后面"评估新框架"的环节按规则终止、不展开——这是规则要求的终止，不是偷懒。

**第二问：不重建的话，三种喂法选谁？**

答：**选 A′。** 三个理由：

1. A 现在**根本没实现**——仓库里现有的只是"删字段、压明细"，不是按相关性配菜；
2. A′ 要的零件**家里全有**，而且都有正在用的先例：交卷表里加必填栏、只能勾给定编号，现有表格就有同款；"把本轮真实编号清单塞进表格、让 AI 打不出清单外的值"这招，论点/修订环节的冲突编号已经在用；
3. A′ 只比 A 多填一栏，**不多跑一趟、不添新故障点**。

一条诚实的限定：DeepSeek 有时会不按表格交卷（它的规则允许它直接交文字），那种情况靠"必填检查 + 重试"兜底。所以 A′ 不是百分之百的绝对强制——但它没有比 A 多任何新风险。

顺带把账底数摆出来：最近一次真实跑，输入材料 **963,419 token**（token 是 AI 的计费单位），五个书房占 45.7%、治理四站占 30.4%；治理四站收到的那份关键证据清单**四份一模一样**（116,150 字符 × 4），四站提示词 95.2–97.8% 雷同，但公共开头只有约 0.16%——"同样开头只算一次钱"的缓存基本吃不到。**所以"省材料"是真需求；但省多少必须可测，不能拍脑袋。**

**第三问：B 为什么不行？**

答：**四道门槛一道没过。**

1. **没人能证明"事前自己要"比"事后说缺"更值钱。** 反而有成熟做法证明：事后结构化报缺 → 驱动下一轮取料，学术上已有现成组件，和 A′ 是同一个思路；
2. **现在的 DeepSeek 模型，你没法强迫它必须去取材料。** 它默认开思考模式，这个模式下"必须调用工具""指定调哪个工具"两个开关都被官方拒绝；有人关掉思考模式强行指定，长提示词下 **40–60% 会写出坏卷子**；
3. **"B 能省 20%"没有任何证据，反而有反例。** 别人的实测里，多轮来回缓存时好时坏，工具说明书还占了输入账单约 70%；
4. **能不能保住五层隔离和逐字查账，没证实。** 现有查账管道是完备的，但 B 要新增"每轮来回都落盘"，能不能等价做到取决于设计，不能默认。

所以：**B 不是方向错，是现在的模型脾气给不了它一个能接受的失败边界。**

### 没查的、没证实的，如实交代

- 重建部分的第 3/4 问按冻结规则终止（第 0 问为 0），目标框架的关闭能力、迁移成本**未调研**——规则要求的终止，不是遗漏。
- 未证实清单共 5 条，都在技术附录里；最要紧的三条就是上面 B 门槛里的：模型不交表格的精确概率、"事前自己要"不可被替代、"省 20%"。凡没证据的，都没拿来下结论。

## 二、第 1 问：三种做法各自的可审计性所得，值不值代价？

### 三变体一句话
- **A（代码侧检索）**：组装提示词之前，代码按"该站自己声明的问题"做相关性排序、取前 K 条。审计所得 = "代码筛了哪 K 条、依据、排除了哪些"。
- **A′（代码侧深度分档 + 必填缺料回报）**：A 的基础上，在站点**输出表**里加必填字段 `unmet_information_needs`（ref 枚举），模型物理上只能勾系统给过的编号。审计所得 = A 的筛选留痕 + **事后缺料回报**，可直接反哺筛选器。
- **B（模型侧按需取用）**：模型自己发起取用调用，单次调用改成循环。审计所得 = 模型**事前**主动要了哪几条。

### 关键事实
- A 目前**没有实现**：仓库现有裁剪只是"按黑名单删字段 + 压缩超长审计明细"，不是相关性 top-K（`src/agent_analysis/orchestrator.py:7128-7265`）。
- A′ 在现有系统里**全部零件齐备**：
  - 必填 + 枚举 = pydantic `Field(..., ...)` + `Literal`，现有契约已有先例（`src/agent_analysis/contracts.py:2106-2109`）；
  - 新字段自动进提示词（`src/agent_analysis/orchestrator.py:7096-7126`）；
  - **已有"给输出 schema 动态注入本轮真实编号枚举"的生产先例**：thesis/reviser 的 `conflict_id` 就是这么做的（`src/agent_analysis/orchestrator.py:4664-4700`），模型打不出清单外的值；
  - 严格模式 sanitizer 强制 `required` 全覆盖且支持 enum（`src/agent_analysis/llm_engine.py:126-157`）；
  - `_run_stage` 每次 attempt 只调一次模型、无工具结果回灌 → A′ 相对 A **零新增往返、零新增失败面**（`src/agent_analysis/orchestrator.py:5671`；`llm_engine.py:616-622`）。
- 必须诚实说明一个限定：严格模式只在"模型调用工具"时生效；`tool_choice="auto"` 下模型可以不调用工具直接返回文本，此时靠 pydantic 必填校验 + 重试兜底（`llm_engine.py:566-622`）。所以 A′ 是"工具被调用时 schema 强制 + 任何路径 pydantic 兜底"，不是绝对强制——但相对 A 没有新增任何失败面。
- 成本现实：最近真实 run 全量输入 **963,419 token**（L1-L5 占 45.7%，治理四站占 30.4%）；治理四站的 `key_evidence_refs` 四份**逐字节相同**（116,150 字符 ×4）；四站提示词相似度 95.2–97.8%，但公共前缀只有约 0.16%，前缀缓存基本吃不到（证据包 1.4，均为本机复算）。

**按规则第一条（A′ 优先于 A）**：A′ 能满足"放进现有输出表、不加往返、不新增失败面"三个条件，且已有同款工程先例 → **最终建议落在 A′，不落在 A**。

## 三、第 2 问：B 的循环化新增失败面有多大？

**答案：当前 DeepSeek V4 上，B 的失败面无法压到"可忽略"，且三道规则门槛全过不了。**

| 规则门槛 | 证据 | 判定 |
|---|---|---|
| (a) "事前取用意图"的审计价值不可被 A′ 事后回报替代 | 没有任何论文/产品文档直接证明这个强命题——**未证实**；Anthropic 上下文工程明确"预筛 + 按需取用"是混合策略而非唯一正解；S2G-RAG（ACL 2026）证明"事后结构化缺口 → 驱动下一轮检索"是成熟组件，与 A′ 同构 | **不满足** |

| (d) 不破坏五层隔离与字节级审计 | 现有 `prompt_audit` 管道完备（`orchestrator.py:5848-5894`），但 B 需要新增每轮工具回灌审计，能否等价落盘取决于设计——自动满足**未证实** | 可设计，但规则 2 已因 (a)(b)(c) 失败 |

**结论：不建议 B。** B 不是方向错了，而是当前 DeepSeek 模型形态（思考模式 + `tool_choice` 限制 + 缓存行为）给不了它一个可接受的失败边界。
