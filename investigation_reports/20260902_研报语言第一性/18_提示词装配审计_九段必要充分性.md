## 一、答第一问：工具函数全盘喂给 AI，合理吗？

### 先纠正一个事实：模型根本没能力调用工具

`src/agent_analysis/llm_engine.py:566` 的 `kwargs["tools"]` **不是**"给模型一堆数据工具去调用"，而是：

```python
kwargs["tools"] = [{
    "type": "function",
    "function": {
        "name": tool_name,                      # emit_structured_output
        "description": f"Emit the structured {stage or 'stage'} output.",
        "parameters": strict_tool_schema,       # 就是那套 JSON schema
        "strict": True,
    },
}]
```

它是**用 function schema 强制模型输出结构化 JSON 的输出锁**（DeepSeek 专属的 strict function calling）。只有一个工具，参数就是本站的输出 schema。而且 `:627-631` 有兜底：模型不调这个工具就回退到读 `content`。

**结论：所有数据都是装配前算好的，模型是"填空者"，不是"调查者"。**

### 但工具函数的一类字段确实会进 payload

实测 `prompt_audit/*/attempt_1.payload.json`，含这些键名的叶子值会进模型视野：
`notes` / `methodology` / `formula` / `source_boundary` / `state_usage_boundary` / `data_quality` / `MetricAuthority`

| 站 | payload 字符 | 元信息字符 | 占 payload | 含英文元信息条数 |
|---|---|---|---|---|
| L1 | 10,755 | 1,866 | 17.4% | 10 |
| L2 | 20,257 | 3,776 | 18.6% | 34 |
| L3 | 9,739 | 2,375 | 24.4% | 18 |
| L4 | 59,459 | 11,047 | 18.6% | 40 |
| L5 | 10,441 | 2,049 | 19.6% | 6 |
| bridge 及全部下游站 | — | **0** | 0.0% | 0 |

内容实例（全部英文、公式、内部枚举）：

- `get_m7_capex_cycle.value.methodology`（1,260 字）
  `"Primary channel: SEC XBRL company-concept duration facts (10-Q/10-K), which for most filers report fiscal-year-to-date cumulative cash-flow values…"`
- `get_ndx_forward_pe_full_constituent.notes`（679 字）
  `"NTM EPS = w*FY1 EPS + (1-w)*FY2 EPS, w=clip(days to FY1 fiscal year end/365,0,1); index forward PE = 1/sum(nor…"`
- `get_m7_buyback_flow` 的 `state_usage_boundary`（396 字）
  `"Actual repurchase spending is long-horizon balance-sheet/EPS support evidence only (usage=supporting_only); it cannot prove a short-term price bottom…"`

源码位置：`src/tools_L4.py:5503`、`:5639`、`:5887`、`:6314`。

**并且存在同一段文本在一处复制多遍**：`get_m7_buyback_flow` 的 543 字内容同时出现在 `value.formula`、`data_quality.methodology`、`data_quality.formula` 三处。

### 判定

| 问题 | 答案 |
|---|---|
| 工具函数"全盘"喂了吗？ | **没有**。19 万字符是文件全文；实际进模型的是 5 个站合计约 **21,113 字符** |
| 进的这部分合理吗？ | **不合理**。它们是"写给审计员的记账说明"，不是"给分析员的判读材料" |
| 它是黑话主因吗？ | **不是**。占各站总 prompt 仅 3%~5%（L4 最重）。它是**技术腔和英文残留的种子** |
| 影响面 | **只有 L1–L5 五站**，下游八站为零 |

**建议**：这类字段分两类处理——`source_boundary` / `state_usage_boundary`（发言权边界，**分析员必须知道**）→ 翻译成中文短句进 prompt；`methodology` / `formula`（怎么算的，**审计才关心**）→ 不出现在 payload，移进审计区。**但此项属独立工单，不是本轮黑话治理的范围。**

## 二、答第二问：九段拼是否合理、是否必要充分

### 真实结构不是"九段"，是"两段"

每份 prompt 的实际形态只有两个角色消息：

```
role: system  →  # System-Level Constraints（336 字，6 条纪律，13 站逐字相同）
role: user    →  <写作指令若干段> + ## Runtime Input（payload）+ ## 输出字段规格 + ## Response Rules
```

"九段"是 user 消息内部的拼接单元，**各站段数不同**（L1–L5 是 34 个小标题，counter_thesis 只有 12 个）。

### 配比才是真问题

| 站 | 总字符 | payload | payload 占比 | 有 Few-Shot 范例 |
|---|---|---|---|---|
| L1 | 56,129 | 34,198 | 61% | **有**（4 个） |
| L2 | 77,215 | 50,623 | 66% | **有**（4 个） |
| L3 | 43,834 | 25,363 | 58% | **有**（4 个） |
| L4 | 219,819 | 181,548 | 83% | **有**（3 个） |
| L5 | 53,171 | 30,181 | 57% | **有**（4 个） |
| bridge | 153,228 | 138,838 | 91% | 无 |
| thesis | 304,311 | 288,071 | 95% | 无 |
| counter_thesis | 328,853 | 325,763 | **99%** | 无 |
| critic | 168,715 | 162,039 | 96% | 无 |
| reviser | 191,620 | 179,489 | 94% | 无 |
| **final_adjudicator** | **201,858** | **185,240** | **92%** | **无** |
| risk | 144,207 | 136,691 | 95% | 无 |

**不是"段太多"，是"范例与规则倒挂"。**

| 站群 | 给的是 | 每站写作指令 |
|---|---|---|
| L1–L5 | 4 个 Few-Shot（含 `CORRECT OUTPUT` 范例）+ canon + 层契约 | 17%~43% |
| 下游八站（含终审） | **零范例**，纯规则文本 | 1%~9% |

**终审是写门面判决正文的那一站，它有 14 条文风契约**（`final_adjudicator.md:243-257`，写得很到位："判断先行"、"不许陈列数字"、"关键推演摊开一两步，让读者能自己走到结论"、"内部簿记语言不上台面"）**，但一个范例都没有。**

**这印证了 10 号定案的诊断**：病根不是"规矩不够"，是"无作者"。L1–L5 有作品可模仿，下游八站只有条文可遵守——**照条文写出来的东西是合规的，不是有说服力的。**

### 顺带查出的三处具体毛病（都在 `_compose_layer_prompt`，`orchestrator.py:8052-8130`）

1. **同一批字段被讲两遍**：硬编码的 `### 必须新增并认真填写的字段`（892 字）与契约自动生成的 `## 输出字段规格`（1,478 字）**讲的是同一批字段**。前者讲"要写什么"，后者讲"形状是什么"，职责重叠。按 `AGENTS.md`「约束住哪：轨道 > 导出 > 规矩」，前者里有 5 条本可由 schema 承接。
2. **A 段是黑话的直接种子**：`:8091` 写着 `internal_conflict_analysis 必须讨论本层内部指标之间的共振、背离、降噪和优先级` ——**"共振""降噪"就是这么教出来的**（与 `contracts.py` 那句同源）。
3. **结构示例里的占位句在教腔调**：`:8110` `"narrative": "把读数、趋势与分位压缩成一句本层判断。"` ——这是模型看到的第一句"本层判断长什么样"的样例，而它本身是句黑话。

### 判定

"九段拼"本身**不算错**——每段都有明确职责，也做了按层裁剪（canon / few-shot / 指标清单都是动态的，不是全量灌）。**错在三处**：

| 编号 | 毛病 | 性质 |
|---|---|---|
| **N1** | 下游八站零范例，恰好是写人话最重的八站 | **结构缺陷**（配比倒挂） |
| **N2** | 硬编码字段说明与契约字段规格职责重叠 | **冗余**（可删可并） |
| **N3** | 结构示例占位句 + 硬编码写作指令，是黑话的静态种子 | **种子问题**（换示例） |

**回答"是否每个 agent 都需要这九段"**：不需要，而且现在也不是九段都给——canon / few-shot / 层契约**只有 L1–L5 有**。真正的问题是反过来的：**该有的站没有（下游八站缺范例），该瘦的没瘦（L4 塞了 220K）。**

## 三、答第三问：派多个 agent 遍历提示词查黑话，合适吗？

### 不合适。方向错了。

**理由用数据说**：黑话的产地主要不在提示词里，在 **payload 的上游散文**里。

| 站 | payload 字符 | 其中中文散文 | 占 payload |
|---|---|---|---|
| bridge | 66,765 | 33,405 | 50.0% |
| thesis | 128,812 | 54,846 | 42.6% |
| counter_thesis | 150,834 | 65,185 | 43.2% |
| final_adjudicator | 87,866 | 39,191 | **44.6%** |

而这些散文**就是上游模型自己写的**（`synthesis_packet.layer_summaries[].layer_synthesis` / `internal_critic_analysis` 就是 L1–L5 的原文）。链条是：

```
L1-L5 分析员写散文
  → 桥接站 100% 原样收下（其中 50% 是散文）
    → 论题/反方 原样收下（43%）
      → 批评/修订 原样收下
        → 终审 原样收下（44.6%）
          → 终审写出的判决正文
```

**终审写出的那句"近端宽、远端窄"，不是它想出来的，是它从输入里读来的。** 五层分析员用"地心引力""垫子"写下的句子，穿过六道工序，一个字都没被改写。

派十个 agent 逐字读提示词，读的是**合同**；而问题的现场在**案卷**。

### 那你该怎么看？工作量能不能降下来？

**能，而且不用逐字读。** 三个层次，由轻到重：

| 办法 | 你花的时间 | 能看出什么 |
|---|---|---|
| **甲：看配比表**（本文第二节那张） | 3 分钟 | 一眼看出哪一段异常膨胀、哪一站缺范例 |
| **乙：跑 payload 体检脚本** | 0 分钟（我跑） | 量出每站输入里"非分析文本"占多少（英文元信息 / 上游散文 / 重复段） |
| **丙：单站冻结 A/B 盲读** | 一次盲读 | 你唯一必须亲自做的事——判断哪个版本更有说服力 |

**我的建议：甲和乙已经做完了（就是本文），直接进丙。** 你要亲自花的时间只有一件——盲读对比，其余全部可以用脚本机械化。

## 四、为什么 T71 治过一轮黑话，这次还有

这是本文最重要的背景。查 `tests/test_t71_batch2_noise_jargon.py` 头部：

> 对象 run：`t70_glm_check_20260902` 与 `20260905_171025` 的实测病灶——**#4 黑话传染**：prompt 高频无解释内部词直出进输出（「法典」L2 输出直出 7 次、「三明治口径」被原样回抄、「底账」「门脸徽章」进终稿）。
> **修法边界（老板硬约束）：只动模型可见的叫法与清洗行为；宪法字段、检查名、机制一根不动。**

T71 的战果（`WORK_LOG.md:13` 记录）：法典 / 吸收端 / 约束端 / 三明治口径全零、底账归零含 CSS 注释。

**两批词没有交集，因为发现方法不同**：

| | T71（已做） | 17 号（本轮） |
|---|---|---|
| 发现方向 | **从报告输出侧反查**：报告里出现了什么词 | **从静态源正查**：扫所有喂给 agent 的东西 |
| 治的词 | 法典、三明治口径、底账、门脸徽章、吸收端、约束端 | 近端、远端、地心引力、垫子、温度计、闸门、张力、姿态、锚… |
| 结果 | 已归零 | 待治 |

**"正查"能发现"反查"发现不了的东西**——因为模型现场造的比喻词（兑现桥、零垫子、承重墙、独木桥、铸造厂）在静态文件里查不到，只能靠扫"喂进去的东西"再和报告比对才能定位。

**这也回答了你上一轮的追问"这就是完整的静态清单吗"：是。** 而且脚本可复现（见第七节）。

**T71 的边界划分是对的，而且正好适用于你这次的裁决**：

| 类别 | 例子 | 归属 |
|---|---|---|
| 宪法字段 / 机制 / 字段名 | `principal_contradiction`、`typed_conflicts` | **一根不动**（T71 边界） |
| 模型可见的叫法 | 近端、远端、地心引力、垫子、温度计 | **本轮治** |

按这条边界，**"矛盾"自动归入"不动"那一栏**——它不仅是字段名，还是机制名。你爱它，系统也需要它，两不相干。
