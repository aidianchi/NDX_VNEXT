## 3. 依赖图（谁必须等谁）

```
packet → context_brief
  → L1..L5 五层（互相独立 ✅ 可并行）
  → bridge_v1（等五层）
  → inquiry 跨层对质（等五层+bridge_v1）
  → investigation ×3（等 inquiry；互相是否独立待确认）
  → bridge_v2（等 investigation）
  → synthesis_packet（等五层+bridge）
  → hypothesis_competition 正反辩论（等 synthesis）
  → 事件卡 ×10（等 hypothesis_competition：payload 带 competing_hypotheses，orchestrator.py:1653 ❌ 不可与五层并行）
  → evidence_registry → thesis
  → critic / risk（互相独立 ✅ 可并行，小收益）
  → schema_guard → reviser（等 critic+risk）
  → final_adjudicator（终审）
  → 报告三件套（brief / workbench / prompt_inspector）
```

**关键结论**：老板猜测"事件卡和五层并行"在当前架构下**不可行**——事件卡必须拿到竞争假设列表（`competing_hypotheses`，orchestrator.py:1653），而假设列表要等五层→桥接→对质→调查→辩论整条链完成（`_build_hypothesis_competition`，orchestrator.py:2711）。这是数据依赖，不是约定。

### 并发度设计（风险可控的关键）

- 默认 `max_workers = 3`（保守；五层分两批、事件卡分三批），跑顺后经冒烟确认再提到 5。
- 可配置：环境变量 `NDX_STAGE_PARALLELISM` 或 orchestrator 构造参数，`min(worker数, 任务数)`。
- 理由：GLM 开放平台/编码套餐的 RPM/TPM 配额未知，先小并发试水，不赌。

### 实现要点（三处必须处理）

1. **共享 manifest 写冲突**：`stage_manifest.json` 与 `llm_stage_diagnostics.json` 由 `_record_stage_artifact`（read-modify-write 整体写盘）维护，多线程同时写会互相覆盖丢更新。对策：orchestrator 加一把 `threading.Lock`，`_record_stage_artifact` 与 manifest 更新路径统一 `with self._manifest_lock:`；或收集完结果后在主线程统一写。选前者，改动最小。
2. **checkpoint 兼容**：每站 checkpoint 按独立文件落盘（`layer_cards/L1.json`、`event_interpretation_cards/event_*.json`），线程写不同文件，天然无冲突。需回归验证断点续跑（resume 场景下并行站全部命中 checkpoint 时应跳过不调用）。
3. **失败/重试隔离**：`_run_stage` 的重试是单站内循环，并发下每站独立重试互不牵连，无需改。但注意并发失败会放大 API 压力（5 站同时第 2 次重试 = 瞬时 10 请求），故并发度默认 3 + 重试退避已有（attempt 间隔）即够。

## 5. 可选增量（方案 B，本次可不做）

- **critic / risk 并行**（省 ~3 分钟）：两者输入各自独立构建（`_build_governance_input_packet` 分别调），可并。收益小、动点多，建议并入 A 之后的第二轮。
- **investigation ×3 并行**（省 ~6 分钟）：需先确认三站是否互相独立（`_run_controlled_investigations` 按 router 输出逐条跑，疑可并，待代码确认）。
- **数据采集层**：不碰。2026-05 的 yfinance 并发瘫痪事故（SQLite 并发 + 文件句柄耗尽）教训在此，采集层维持现状单线程或既有并发策略，不做新并行。

## 6. 风险矩阵

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| R1 | GLM API 限流（429/配额） | 中 | 重试拖慢甚至失败 | 并发度默认 3；冒烟测 429 率；必要时加信号量限流或退避 |
| R2 | stage_manifest 并发写丢更新 | 确定会发生（如不改） | 断点续跑指纹错乱 | 统一 `threading.Lock` 包裹 manifest 更新 |
| R3 | 日志交错难排查 | 高 | 低（仅体验） | 每站日志加 stage 前缀；可接受 |
| R4 | 输出顺序不确定 | 高 | 无 | 报告装配按文件读取不依赖顺序（已核实） |
| R5 | 并行下同一输入结果与串行不同 | 高 | 无 | LLM 本身非确定，串行也不可逐字复现；闸门是形状校验与顺序无关 |
| R6 | 断点续跑并行兼容性 | 低 | 中 | 新增红灯测试：resume 场景全 checkpoint 命中时零 LLM 调用 |
| R7 | 并发失败放大 API 压力 | 低 | 低 | 并发度保守 + 单站重试已隔离 |

## 7. 验证方案（先证明不坏，再上生产）

1. **单测（先红后绿）**：
   - 用 mock LLM，5 层并发跑，断言：5 个卡文件齐全、stage_manifest 完整无丢、无写异常（红灯：加 10ms sleep 放大竞态仍绿）。
   - 事件卡同理（mock 10 个事件）。
   - resume 场景：checkpoint 全命中时断言零 LLM 调用。
2. **冒烟**：真实 GLM 下 3 并发 × 3 次调用，记录 429/超时率，决定并发度上限。
3. **对照跑**：同一 snapshot（`--data_json` 指定同一快照）串行版 vs 并行版各跑一次，比对：
   - 耗时差（目标 ≥40 分钟）；
   - 闸门全绿（25+1 项）；
   - 五层卡/事件卡质量抽查（人工或 LLM 审，确认无劣化）；
   - 429 次数。
4. **灰度**：默认并发度 3 跑一次真实 run 验收，稳定后提到 5。

## 8. 回滚

改动集中在两处循环 + 一把锁，回滚 = 还原两个函数，秒级。不影响已落盘产物。

## 9. 明确不做

- 依赖链（bridge → inquiry → investigation → hypothesis → 事件卡）不动。
- 不改事件卡契约（不把 competing_hypotheses 改成静态假设——那是架构改造，另立题）。
- 不做全链 DAG 调度器重构（收益边际，违背外科手术式收敛）。
- 采集层不做新并行（历史事故教训）。
