# T54 规范 02：全链编号规范（批 4 前置）

日期：2026-08-17。上游：`01_机械字段清点.md` 批 4。原则：机械字段不出答卷——编号（身份名）由代码发，模型只填需要判断的内容；闸门只守代码装配不到的地方。

## 1. 权威容器

**`typed_conflicts` 是冲突的唯一权威容器。** legacy `conflicts` 是兼容导出物，不再由模型填写，也不再与 typed 并存互算——由代码从 typed **反向重建**（conflict_id/conflict_type/severity/description/implication/involved_layers 逐字段映射）。双容器同源后，synthesis_packet 的 `high_severity_conflicts` 与 `high_severity_typed_conflicts` 条目集恒一致，PC-23 从"报警器"转为"落盘回归看守"（语义不放松：产物被手工改动或旧格式回流仍报警）。

模型只填 legacy 不填 typed 的旧形态仍兼容：先按既有 `_derive_typed_conflicts` 正向派生 typed，再统一走"重发 id + 反向重建 legacy"。

本规范取代 08-17 工作区的"同长同 type 逐对对齐"止血逻辑（`conflict_ids_aligned_to_typed_conflicts`）——对齐是双填写时代的补丁，反向重建是单权威时代的正解；对齐代码同批移除。

## 2. id 发放规则

| 容器 | id 形态 | 发放点 |
|---|---|---|
| `typed_conflicts[]` | `TC_01…` 按序 | bridge 归一化（`_normalize_payload` bridge 段） |
| `resonance_chains[]` | `RC_01…` 按序 | 同上 |
| `transmission_paths[]` | `TP_01…` 按序（去重后） | 同上 |
| counter `hypotheses[]` | `hyp_counter_<sha1(文本)[:10]>`（内容哈希，沿用既有 `_stable_hypothesis_id`；同文同 id、幂等，LLM 稿与确定性兜底稿同构） | `_build_counter_thesis` 落盘前 |

- 一律重发，不保留模型自填 id（包括看起来像规约的 TC_01——重发是幂等的）。
- **不静默丢弃**：模型原 id 与新 id 的映射写入 `normalization_notes`（`conflict_ids_reassigned_by_code:TC_01<=模型原id,…`）；counter 侧模型原文留在 prompt_audit raw response。
- id 的生命周期是单 run 内：synthesis_packet 在 bridge 归一化之后构建，thesis/reviser/final 看到的都是重发后的 id，跨站引用一致。跨 run 稳定性不作要求（PC 检查均为单 run 内身份比对）。

## 3. 引用重接（同一 payload 内）

重发 typed id 后，bridge 产物内对旧 id 的**精确匹配**引用按 old→new 映射改写：

- `principal_contradiction.contradiction_id` 与 `conflict_refs[]`；
- `secondary_contradictions[].contradiction_id`；
- `price_reflection_map[].target`（仅当与旧 id 逐字相等时）。

对不上映射的引用**原样保留**，交给既有校验/闸门（schema guard 软报、strict enum 硬拦）——不猜、不按位置硬配（与批 5 同一纪律）。

`involved_layers` 顺带机械化：`evidence_refs` 非空时按其 `L[1-5]` 前缀派生覆盖（涉及层 = 证据涉及层，可审计）；refs 为空时保留模型归一化值。

## 4. 下游引用方式

- thesis / reviser：strict tool schema 的 conflict_id enum 选单（既有，`_constrain_thesis_retained_conflict_id_enum` / `_constrain_reviser_conflict_id_enum`），选单来自 synthesis_packet（重发后的 id）。
- final：`_validate_final_conflict_responses` 按编号认亲（既有）。
- 枚举字段拼写：`TimeHorizonView.horizon`、`PortfolioAction.bucket` 的合法值是固定三档；模型拼写出界时归一化按位置兜底值回正并 log（不发明别名映射）。

## 5. 模型异议通道

- "哪条冲突是主要矛盾/该留哪些冲突"是判断（C 类），不在本规范范围。
- 模型对编号本身无话事权；它若认为两条冲突该合并/拆分，写在 `unresolved_questions` 或冲突描述里，进审计区。
- 重发映射留痕见第 2 节。

## 6. 设计岔路（需老板拍板，本批跳过）

**thesis/final 侧手填 conflict_id 在非 strict 路径下无效时怎么办。** strict 路径有 enum 选单硬拦；非 strict 路径（默认）下模型把 id 抄错时，代码无法确定性回正（不知道它指的是哪一条），只剩两个选项：

- A. 新增硬校验：retained_conflicts 的 conflict_id 非空且不在候选集 → 拒收重试。风险：桥零冲突或模型新发现冲突（按契约应留空）的边界情形要处理，可能增加重试烧毁；
- B. 维持现状：保留模型值，schema guard 软报（consistency_issues），PC-23 落盘比对兜底。

本批按 B 不动（纪律：不擅自扩方案）。A/B 取舍涉及"冲突认亲失败时该烧重试还是该软放行"，建议老板定。

**后续裁决（2026-08-19，O15）**：老板拍板采第三方案（超出当时 A/B 框）——**模型只报序号，代码展开成编号**。typed_conflicts 的编号本就由代码按序发放（TC_01…），序号即编号：thesis/reviser 的 `Conflict` 模型面向字段改为 `conflict_ordinal`（1-based，清单即 `_collect_thesis_conflict_id_candidates` 的输出去重保序版，提示词末尾附「冲突清单（按序号引用）」），解析后由代码映射回 `conflict_id`；越界/类型错误走既有带反馈重试通道，清单为空时序号必须为 null。当时 §3 否决的"按位置硬配"针对的是"代码按位置猜模型意图"，与本方案"模型报位置、代码做映射"不冲突。T58 施工。final 站不动：`contradiction_id` 是"优先引用"性质的软引用，且 T42③ 的硬检查是"高严重度冲突编号出现在终审文本"的存在性检查，按编号认亲语义不变。

## 7. 批 5/6 联动说明

- 批 5（function_id/metric 抄回配对）遵循同一纪律：模型自报 + 代码校验回正；仅当拼写错误有**唯一高相似近邻**时回正（留 log），否则校验器拒收重试；绝不按列表位置硬配。
- 批 6 两项评估结论（超出清点预判，跳过）：
  - **risk 矩阵键集**：A-M 清单的唯一事实源目前在 `cross_layer_bridge.md` 的表格里（PC-B 解析提示词表格，persistent_checks_b.py:628-651），代码侧另立常量即造双源——正是 `PRICE_REFLECTION_CATEGORY_KEYS` 注释（contracts.py:1026-1039）警告过的反模式；单源化需要"提示词表格由代码生成"的大改，不在本批。
