# T54 清点 01：25 站 LLM 答卷机械字段清点（只清点，不改代码）

日期：2026-08-17。依据原则（总纲常驻边界，老板 08-17 定）：

> **机械字段不出答卷**：凡代码能确定性生成或回填的字段（身份名、枚举值、编号、时间戳、引用键），一律由代码装配，不让模型填；模型只回答需要判断的问题。闸门只守代码装配不到的地方。

本文只做清点与改造建议，不改 `src/`。08-16 的 permission_type 法典回正是过渡安全带，T54 是根治。

## 分类口径

- **A 类**：已由代码装配/回填，模型填了也会被覆盖或兜底——只列机制位置，不再动。
- **B 类**：模型在填、但代码能确定性定（照抄输入、枚举表、canon、派生规则、固定字面量、编号、时间戳）——改造对象。
- **C 类**：真正需要判断的字段（narrative、reasoning、状态评估、枚举里的"选哪个"含判断成分者）——不动。
- **混合类（refs 列表）**：`evidence_refs`/`event_refs`/`supports_hypotheses` 这类"引用集合"字段，**选哪些是判断（C），成员身份合法集代码可验（校验器已在做）**。它们不属于"代码能定值"的 B，不列入改造，只在备注里说明。例外：当合法集只有一个必然答案时（如 IA 的 stance_echo、IndicatorAnalysis 的自身 evidence_ref），算 B。

- **B 类字段位总数：51**（L1-L5 13、bridge 9、thesis 5、counter 6、risk 1、reviser 1、final 4、event 卡 2、IA 6、CI 4）。

## 分批施工次序建议（风险从小到大）

1. **批 1｜固定字面量与时间戳类**（零判断、零配对）：counter 的 schema_version/independence_boundary/input_refs/forbidden_context_refs/prompt_input_audit；IA 的 schema_version/judgment_object；final 的 token_usage 与 ClaimLedger 字面量；CI 四件。值唯一确定，测试好写，先立"代码装配"的工程范式（装配层落点、留痕格式、提示词删字段流程）。
2. **批 2｜payload 单值直装**：event 卡 event_type/entities；LayerCard.layer；QualitySelfCheck.covered_function_ids/coverage_complete；reviser.revision_claimed_fields（代码 diff 替代模型自报，PC-03 同步改口径）。
3. **批 3｜canon 无条件覆盖**：IndicatorAnalysis 的 permission_type/canonical_question/misread_guards/cross_validation_targets/falsifiers/core_vs_tactical_boundary 从"缺省回填/非枚举回正"扩为无条件法典覆盖；配套上线 `canon_dispute` 异议通道。机制已在（orchestrator.py:8288-8315），是小步，但要先把异议通道定稿。
4. **批 4｜编号体系**：bridge/thesis/final 的 conflict_id/chain_id/path_id/contradiction_id/conflict_refs 与 counter 的 hypothesis_id/source；含 legacy `conflicts` 由代码反向派生的冗余收敛。需先定全链编号规范，动 PC-23 与 schema guard，跨站身份链最敏感。
5. **批 5｜抄回配对**：IndicatorAnalysis.function_id/metric、CoreFact.metric。活证据最强，但列表无顺序保证，需先定配对策略（建议：模型自报 function_id + 代码对输入键集校验回正，配不上按未知拒收并重试，而不是代码硬配）。若老板想先吃收益可与批 3 对调，但配对规则必须先定。
6. **批 6｜结构性**：risk 矩阵键集骨架、CoreFact 值骨架代码装配——动 schema 形状，最后做。

每批都要同步：提示词模板删掉对应字段的填写要求、校验器/strict tool schema、PC 系列检查口径、配餐单文档、测试。改 schema 一律先红后绿。

## 风险最大的三个字段

1. **`IndicatorAnalysis.function_id`/`metric`（批 5）**：收益最大（08-16 三连抄错直接打红 PC-19 类检查）也最容易改错——`indicator_analyses` 是列表，与输入键集无一一顺序，模型漏分析某指标时"代码硬配"会把张冠李戴从模型错误变成系统错误。正确姿势是"模型自报 + 代码校验回正"，不是纯装配；配对歧义必须走拒收重试而不是猜。
2. **IA `stance_echo`（批 1）**：看着最简单（逐字复制），但它是"数据判决是锚、第三层无权改判"红线的载体。现状"模型填 + 不等即 raise"（integrated_synthesis_report.py:643）能捕获模型**想改判的意图信号**；改成代码装配后这个信号消失——模型对数据判决的异议必须改道 `conflict_matrix`/`unexplained`（提示词已有此通道，:22），施工时要验证异议真的写得进去、不被静默吞掉。
3. **bridge 双 id 体系（批 4）**：`conflicts` 与 `typed_conflicts` 是设计层冗余，08-17 的 id 对齐只是止血。根治（模型只填 typed、legacy 代码反向派生）一动就是 synthesis_packet 双容器、PC-23、schema guard、thesis/critic/risk/final 四方消费面的连环改；改错=冲突身份链断裂、跨站审计失忆。必须单独立项、一次改透，不能夹在其他批里顺手做。

## 模型异议通道总设计（防"形式拒收内容"）

- 每个被代码接管的字段，模型端配一条**同站自由文本异议位**：单指标级 `canon_dispute`、冲突级 `unresolved_questions`（已有）、IA 级 `conflict_matrix`/`unexplained`（已有）、thesis 级 `notes`。
- 异议位内容进 prompt_audit 与审计区，不进主链值；新增一条 PC 巡检口径（异议非空时人读），防"模型反复异议同一字段而无人知"。
- 红线：异议通道只承接表达，不改变装配值；装配值错了改 canon/payload 数据源，不改模型提示词。
