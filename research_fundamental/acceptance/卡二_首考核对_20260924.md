# 卡二·首考上下文菜单核对记录（2026-09-24）

## 这是什么

理想版说明书第六章规定：卡二（上下文菜单核对）不是常驻闸门，但"一处判断生产线重建或重大修改后的头几次运行"必须动用。首考 run 20260923_193318 是重建后第一次真实跑，本记录补上这笔欠账。核对材料是该 run 的 prompt_audit 逐字落盘件，对照菜单表（`research_fundamental/Q8_whitelist/ideal_blueprint.md` 2.1 节）。六个核对点里机械可判的全部机器执行，结果如下。

## 通过项（机器层全绿的部分）

| 核对点 | 结果 |
|---|---|
| 层间隔离：L1-L5 不得见其他层与事件材料 | 五层全部通过：搜不到其他层的证据引用前缀与任何事件材料标记 |
| 风险哨兵隔离：不得见论点论证 | 通过：哨兵提示词里搜不到主论点与论证文本（25,763 字，小体积本身就说明没灌） |
| 自查清单不进提示词 | 通过：全部 25 份落盘提示词零命中 |
| 摆位：职责在开头、输出硬约束在结尾 | L1、正方、终审通过 |

## 记红项

**反方假说站提示词 349,645 字，超过菜单表记录在案的事故线。** 菜单表原话：反方站曾被灌 32.4 万字符审计底账、深入性能退化区，"这个事故不得重演"。首考实测：反方 34.96 万（其中 Runtime Input 一块 34.55 万）、正方 31.79 万（Input 30.56 万）、桥接 17.58 万、修订 16.54 万、批评 13.87 万。说明书与纪律只占零头，胀的全是输入材料。菜单纪律里"每块材料进上下文前先答'不喂它会怎样'"这一项，在反方与正方两站没有过关的证据。这是首考机器层最实质的扣分，也是"档案室接力/菜单瘦身"讨论的实证：这五站正是推（push）超过优雅投喂尺寸的地方。

## 待人工复核一处

综合裁决（IA）站提示词结尾 900 字符里搜不到输出硬约束标志（其它站都有）。可能是该站走另一条装配路径、摆位纪律未覆盖到；也可能它本来就不吃这套摆位。差异本身先留痕，定性留给复核。

## 边界声明

本核对只覆盖机械可判的六个点；"每块材料能答不喂它会怎样"的逐块答辩、菜单表登记项与实际发送项的逐一对账，属于需要读懂内容的判断活，留给老板复核时抽查。本记录不改动任何生产线代码与说明书，仅留痕。

## 红项解剖（同日晚补）

体量红项的祸首定位到字段级：反方站输入 JSON 34.55 万字里，`synthesis_packet_without_self_reference` 占 22.3 万，其中 **evidence_index 一个键 16.4 万**——108 条证据，每条带着全套审计信封（一句叙事约 350 字，外加 reasoning_process、first_principles_chain、cross_validation_targets、misread_guards、falsifiers 等约 550 字审计字段）。正方站同构（synthesis_packet 23.2 万）。

菜单表给辩论双站的规定是"证据菜单（可用证据的条目化清单）"，不是证据索引的全量审计明细——当年的 32.4 万事故是同一种东西。修复候选（待老板拍板，不动手）：装配器给正反两站生成"证据菜单"视图——每条只留编号+指标+读数+状态+权限+一句叙事（约 362 字/条），审计明细留在层卡档案供查阅。

投影尺寸实算（同一份首考输入、同一序列化格式重打包，非估算）：反方站 345,524 → 169,137 字（-51%），正方站 317,914 → 141,527 字（-55%）。（更正：本节上一版写的"35 万→12 万"是口算高估，以实算为准。）注意含义：菜单化把剂量减半，但 17 万字仍在性能退化区——它是卫生，不是根治；根治要靠"档案室接力"那类拉（pull）形态或更狠的菜单裁剪。

## 附一：IA 摆位复核结论（同日）

综合裁决站的硬约束确实在前段（第 4,145 字符处），结尾是引用白名单材料——与 2.1 通用摆位纪律（硬约束放结尾黄金位）不一致，差异属实。但该站走 integrated_synthesis_report 的另一条装配路径，且菜单表对它写明"现状与文献对齐最好、菜单原样继承"。定性：**偏差不等于病，留档不定罪**；若未来 IA 输出出现结构性毛病，此处是第一个疑点。

## 附二：卡一第〇档离线补扫（首考，扫描器未接线、仅出数）

首考的生造词黑名单机器层从未正式执行。本次用既有扫描器（config/coined_word_blacklist.json，33 词在册）离线补扫首考全部产物，结果：

- **读者可见面干净**：简报 HTML 全文 84,048 字零命中；五张层卡零命中。
- **在册词"约束面"沿主链传播，合计 34 处**：桥接备忘录 bridge_0 ×6 是全链最早命中点，下游 synthesis_packet ×9、bridge_v2 ×5、analysis_revised ×3、thesis_draft ×3、pure_data_report ×3、final_adjudication ×3、logic_vnext ×2 全部是它的传播。此前手工记录的"6 处未拦"只是桥接站一站的数。
- 含义：黑名单若接线，**最佳拦截位是桥接站出口**——在那里拦一次，下游七份产物全部免疫。这为"扫描器接不接、接在哪"的挂起裁决提供了实测依据（注意：本补扫只出数，生产代码未做任何改动）。

## 附三：核对器脚本化（同日晚）

本卡的六个机械核对点已固化为 `scripts/context_menu_check.py`（只读不写，不是生产闸门），验证期第 2~5 期每期跑 `.venv/bin/python scripts/context_menu_check.py output/analysis/vnext/<run_id>` 即出同款报告。脚本对首考的复跑结果与本记录完全一致（含事件总结站缺声明、IA 结尾无硬约束标志、反方站超事故线三处）。全量测试 1592 项绿。

## 附四：体量红项修复落地（同日晚，老板拍板"修"）

老板裁决三件事：①摘要位残留词选 b（不治，交第 2 期真实跑观察）；③反方站超限要修；②第 2 期真实跑排在③修完之后。本附记③的落地。

**修法**：`orchestrator.py` 的 `_slim_evidence_index_for_prompt` 从"只压 field_value 超长列表"升级为"证据菜单视图"——正反两站每条证据只留编号（ref key 不动）+ 指标 + 读数 + 状态 + 权限 + 一句叙事；reasoning_process / first_principles_chain / cross_validation_targets / misread_guards / falsifiers / core_vs_tactical_boundary / canonical_question / cross_layer_implications / risk_flags 审计信封整批不进 prompt，完整明细仍留在落盘 synthesis_packet.json / evidence_registry.json。子条目（parent#field）的 field_authority 只留 usage 权限档。说明书本来就管这块叫"证据菜单"（thesis_builder.md「## 输入」），此改让代码形态与说明书措辞一致。

**实算效果（首考素材重打包，序列化格式与真实 prompt 一致，json.dumps indent=2）**：

| 站位 | 首考实测（修复前管道） | 修复后实算 | 降幅 |
|---|---|---|---|
| 正方站输入 JSON | 317,914 字 | 224,035 字 | -30% |
| 反方站输入 JSON | 345,524 字 | 263,946 字 | -24% |

**对前面投影数字的更正**：红项解剖一节的"反方→16.9 万、正方→14.2 万（-51%/-55%）"是术前投影，高估了降幅——实算只到 -24%/-30%。差距来源：投影按"362 字/条"估菜单条目，实算菜单条目均 1,174 字/条，因为子条目的 field_value 聚合读数（覆盖率、窗口统计等，合计 4.4 万字）按"读数"口径保留，投影时没算进菜单。以实算为准。

**红项判定**：反方站输入降到 26.4 万字，加说明书正文后约 26.8 万，回到 32.4 万事故线下方，首考红灯熄灭。但按菜单表自己的口径，17 万字以上仍属性能退化区——本修复是卫生不是根治，根治归"档案室接力"那条老板主持的原则线。

**验证**：新增菜单视图行为锁定测试（`test_slim_evidence_index_for_prompt_projects_menu_view`：ref key 集合逐字不变、审计信封字段整批消失、子条目权限档只留 usage、core_facts 兜底条目原样放行）；既有三条瘦身管道测试（聚合字段逐字节保留、超长列表压摘要、端到端落盘）原样通过；全量 1593 项绿。
